## Problem

The 2026-10-21 source re-audit found that Spec 0068 has delivered central dense field styling, 14/24 tokens, selectable Admin read-only values, measured value viewports and five-editor Cancel / Save behaviour. Those resolved findings must not be reimplemented. Remaining consumers still override central decoration, omit visible labels, expose prohibited tooltips, silently reject calendar years or lose recoverable input. Admin Search remains explicit-submit and clears selection, and visible Search shortcut cues are not consistently implemented. [L1]

The subsequently adopted 2026-10-20 dropdown supplement also requires a shared selection-only presentation. Existing Flutter dropdowns and menu-based value selectors have inconsistent boxes, menu typography, selected/focus feedback, sizing and dismissal ownership. Copying the starter's widgets/options or treating its human acceptance as Peak Bagger acceptance would not establish local compliance. [L2]

## Proposed Outcome

Complete the remaining text-field alignment and migrate existing selection-only single-value dropdowns to centrally owned presentation while preserving their feature-owned values, validation, persistence and domain operations. Include live, draft-preserving Admin Search; contextual Search shortcuts; recoverable modal submission; and the exact labels, unavailable-choice presentation and keyboard behaviour resolved in this interview. Preserve macOS/Desktop wide scope and the existing ObjectBox/Riverpod/GoRouter foundations. [L1] [L2] [L3] [L4] [L5] [L6] [L7] [L8] [L9] [L10]

This Spec targets compliance with the written local contract, not pixel-identical template parity. Saving these documents implements no runtime behaviour and creates no Work Items.

## User Stories

1. As a user entering data, I can identify every field, read complete validation feedback and use scaled text without losing my input. [L1] [L3] [L8]
2. As an administrator, I can filter committed records immediately without Search closing or replacing the record/draft I am editing. [L1] [L5]
3. As a keyboard user, I can use Cmd+F in the active Search context without affecting obscured, unavailable or mutation-locked surfaces. [L6]
4. As a user importing a Peak List or saving an API key, I can recover from a failed submission using the retained dialog input, without duplicate operations or premature success. [L4]
5. As a user selecting an existing value, I see a consistent labelled field or explicitly configured accessible icon-only trigger with a complete, readable shared menu, and can navigate without committing until activation. [L2] [L9] See approved refinement decision 5.
6. As a Peak List user, I can distinguish an unavailable retained Difficulty selection and understand Rating's minimum thresholds without an implicit filter reset. [L7] [L10]

### R3. Validation, tooltip exclusion and terminology

1. Provide complete beside-field validation with soft wrapping, not default ellipsis, a clipped fixed-height error area or an arbitrary hidden tail. Own the common policy centrally or through a common wrapping error presentation. Labels/errors remain outside editable content viewport caps and reachable through actual form scrolling. 2. No tooltips on text fields or their associated controls, including Search prefixes/actions, Points/Walking Speed adjustment controls, labelled-field dropdown indicators and field-associated calendar navigation/choice controls. Keep meaningful semantic names without relying on tooltips. R10.11's standalone icon-only trigger is a menu action, not a text-field-associated control, and retains its meaningful accessible name and desktop tooltip. Do not blanket-remove tooltips from unrelated actions or surface-level Close/Edit controls where the standard permits/requires them. [L1] [L2] See approved refinement decision 5.

Ordinary inputs/dropdowns receive no Search icon. Remove Admin's trailing Search submit action. Preserve feature-level Save/Cancel/Import/Apply actions; these are operation boundaries, not prohibited individual field submit buttons. [L1] [L2]

### R6. Pending inputs and recoverable drafts across existing forms

1. Fields and associated adjustment/selection controls honour their feature's current operation lock, not merely the visible Save button. In particular protect Add/Edit Peak-list inputs, Points and their callbacks while saving, route-name input while saving, and affected Admin inputs. Reject duplicate/stale action callbacks before awaited work and after lock changes; do not add another competing draft owner. Preserve existing permitted cancellation and persistence boundaries unless R6.4–6 or R7 expressly changes them. [L1] [L2]
2. Retain input through validation/operation failure and subsequent theme/resize rebuilds. Do not replace drafts from a new filtered result list or synchronise committed values over focused edits. Keep controllers/focus nodes explicitly owned and disposed. [L1] [L4] [L5]
3. Preserve field-specific behaviour such as Points limits, peak duration parsing, and overlay Opacity's approved invalid-entry reversion on focus loss. Do not replace domain validation with generic validators or make a valid optional field required. [L1]
4. **Coordinated Admin Delete lifecycle — approved refinement decision 1:** for the existing `Peak`, `NaturalFeature`, `Contact`, `GpxTrack`, `Route` and `Waypoints` deletion actions, acquire one authoritative Delete gate before the first awaited confirmation or preparation. Reject a new attempt while Save or Delete is pending. Hold protection through confirmation, preparation, mutation, existing post-delete domain synchronisation and the resulting refresh; release it when the attempt completes, is cancelled, is blocked by existing relationship rules or fails. Preserve existing deletion coverage, relationships and domain operations.
5. While that Delete gate is held, protect parent Search and Cmd+F, editable inputs and associated controls, row/entity/mode/sort selection, other mutations including Save, parent cancellation/dismissal and navigation away from Admin. Apply the existing retained-shell Save protection to Delete as well, including side-menu/shell changes, supported keyboard/back paths and programmatic departure. Check the current authoritative gate before action/focus/scroll, including captured callbacks before rebuild; never queue or replay blocked actions. Keep the confirmation's own **Cancel / Delete** controls and permitted confirmation dismissal usable; likewise keep any existing blocker/error acknowledgement dismissible. Closing that child surface must not bypass parent protection or cascade into editor cancellation/navigation.
6. Confirmation Cancel, relationship blocking and failure before confirmed deletion preserve the query, selected identity, details/editor and sole unsaved draft. Once storage confirms deletion, clear details/draft for that deleted record only; deleting another record preserves the selected record's draft independently of filtered-row membership. **Approved refinement decision 4:** record the confirmed deletion outcome separately from subsequent domain synchronisation and Admin refresh. In particular, `GpxTrack` removal precedes `mapNotifier.deleteTrack`'s remaining-Track read/PeaksBagged synchronisation; failure there is not a failed or rolled-back Track deletion. Explain that deletion succeeded but synchronisation or refresh failed, keep the deleted record unavailable in details/editing, preserve the query and unrelated selected record/draft, and offer a labelled **Retry** for only the incomplete synchronisation and/or refresh. Never replay deletion, its confirmation or already completed destructive work. Acquire the same authoritative protection before awaited recovery and release it on success/failure, with actionable feedback retained for another recovery attempt. This clarifies outcome/recovery ownership without changing domain transaction boundaries or adding Background Jobs Retry.

### R7. Import Peak List and API key dialog completion

Check the lock at action boundaries, not only after rebuild. Show visible pending feedback. [L4]
2. Import retains the current duplicate-name confirmation and its usable confirmation/cancellation controls while the parent operation is protected. A rejected confirmation returns to the retained form without starting work. Do not deadlock or globally suppress the confirmation's own dismissal. Release the attempt lock when the attempt ends without acceptance. [L4]
3. On recoverable pre-acceptance failure retain selected CSV and list name, keep the dialog mounted, show actionable feedback without raw exceptions as the only guidance, and re-enable **Import** and **Cancel**. Close only after the app-owned Background Jobs starter accepts the work. Once accepted, preserve Spec 0011: background work outlives the initiating dialog, later failures belong to existing Jobs/SnackBar reporting, no cancellation/replayable-input retention or Jobs-panel Retry is added. [L4]

On failure retain the typed key in the dialog, keep the previously saved/effective key active, provide retry guidance and re-enable **Save / Cancel**. ### R8. Local tile server base URL field

1. Inherit central field styling and URL input affordances. Show syntax errors beside the retained field using the existing guidance **Enter a valid http or https base URL.** Keep the saved URL and validation status visible. Guard repeated Save/Retry/Clear or conflicting changes before awaited preference preparation, not only once network validation is underway. [L1]
2. Preserve the existing **Save / Retry / Clear** operation boundary, URL/capability contract, stored snapshot policy and feature states: **Empty**, **Invalid URL syntax**, **Validating**, **Live validated**, **Restored snapshot**, **Validation failed**. Preserve network-failure retry/fallback behaviour and previously specified save-before-validation semantics; do not apply the API-key rollback rule to a syntactically valid saved URL whose subsequent capability request fails. [L1]
3. Keep actionable errors and the typed draft after recoverable persistence/network failures, reject stale completion and avoid unowned async UI work. No automatic background probes, Local Topo authentication fields or unrelated service redesign is added. [L1]
4. **Persistence failure boundaries — approved refinement decision 2:** do not assume the URL, snapshot and validation-status preference writes/removals are transactional. Apply these phase-specific outcomes while retaining R8.2's save-before-network-validation boundary:

   | Failure point | Required resulting state and recovery |
   | --- | --- |
   | Before the URL is saved | Keep the previous confirmed saved/effective configuration and retain the typed draft for **Save** retry. |
   | After the URL is saved, including subsequent snapshot cleanup or status persistence | Keep the newly saved URL. Never use a snapshot belonging to the previous URL; report the incomplete operation and retain the confirmed saved URL as the validation **Retry** target. |
   | Network capability validation fails | Retain the saved URL, remove active capability availability and use the existing basemap fallback/retry policy. Do not roll back a successfully saved URL. |
   | Persisting successful validation's snapshot or status fails | Retain the saved URL; do not claim **Live validated** or activate an unpersisted new snapshot. Show a persistence failure and offer validation **Retry** against the confirmed saved URL. |
   | Clear partially fails | Do not claim successful clearing. Reconcile the remaining stored configuration, deactivate inconsistent snapshots and allow **Clear** retry. |

5. For every R8.4 outcome, retain the typed draft, release the attempt lock, provide actionable feedback and treat false preference write/removal results like exceptions. Keep saved/effective presentation consistent with confirmed storage outcomes, reading back when necessary; if storage consistency cannot be confirmed, disable Local Topo availability and use the existing safe basemap fallback rather than an uncertain configuration. Distinguish persistence errors from network-validation errors and successful completion; do not leave controls indefinitely pending or add a new preference/storage migration. These rules clarify preference recovery, not domain transaction or Background Jobs partial-success semantics.
