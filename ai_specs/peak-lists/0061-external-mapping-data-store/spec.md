## Problem

Peak Bagger bundles or references mapping data from the repository's `assets/` directory, including regional peak data, polygons, route-graph highway exports, TasMap data, and DEMs. This makes the Flutter bundle unnecessarily large and leaves source data ownership split between the app repository and local data folders. The current external store contains the moved data but app loaders, tool defaults, and manifests still rely on `assets/...` paths.

## Proposed Outcome

Peak Bagger is an explicitly macOS-only local app that reads all non-UI mapping data, including Natural Features, from the app-read-only Mapping data store at `/Volumes/Services/Mapping`. The external Mapping data manifest pair is the single runtime source of truth: `region_manifest.json` is the primary catalog, while `Polygons/manifest.json` is the required authority for optional polygon-display files. Startup blocks with recoverable, exact-path feedback when the store is unavailable or incomplete; already loaded state remains intact if the store disappears later. [L1] [L2] [L3] [L4] [L5] [L6]

## User Stories

1. As the local user, I can launch Peak Bagger only when its Mapping data store is available, so maps, regional peaks, routing, TasMap, Natural Features, and elevation inputs are not silently partial.
2. As the local user, I can reconnect an unavailable Mapping data store and press `Retry` without restarting the app or losing persisted data.
3. As the maintainer, I can prepare mapping datasets outside the Flutter repository and know that the app will only consume files named by the store-relative manifest pair.

## Technical Decisions

1. Add one shared Mapping data store path and manifest-reader boundary. Production uses the fixed macOS root; constructors or providers may accept an injected root, filesystem, text reader, platform check, and app-exit action only as deterministic test seams. Expose the immutable catalog through `mappingCatalogProvider`, overridden only inside the ready `ProviderScope`; UI consumers read or watch that provider, and services receive `MappingCatalog` through constructors. Do not retain a global catalog fallback. [L3] [L7]
2. Parse exactly top-level `tasmap`, `naturalFeatures`, `demSources`, and `routingCoverages` as manifest metadata, never as regions; reject other unknown metadata. `tasmap.catalog` and `naturalFeatures.catalog` are required non-empty safe store-relative paths. Every other root entry is a region and must satisfy the base schema plus the applicable facets below. `showInPeakList` accepts only a boolean or the strings `true` and `false`; `poly`, `maps`, and `mapSet` are required lists and may be empty; `peakListFilterAliases`, `ISO_3166-1`, and `ISO_3166-2` are optional typed metadata.

| Facet | Discriminator | Additional required fields | Restrictions |
| --- | --- | --- | --- |
| Base region | Every non-metadata root entry | non-empty `name`, `shortName`, and valid `priority`; `showInPeakList`, `poly`, `maps`, and `mapSet` | None |
| Seedable | `composite` is absent or `false` and `seedOnStartup` is absent or not `false` | non-empty `fingerprint` and non-empty `peaks` | May also be a routing source |
| Routing source | non-empty `routingCoverage` | a declared routing coverage and non-empty `highways` | May have no polygons and may also be seedable |
| Supporting | `seedOnStartup` is `false` and `routingCoverage` is absent | base fields only | Must not define `fingerprint`, `peaks`, or `highways` |
| Composite | `composite` is `true` | base fields only | Must not define `fingerprint`, `routingCoverage`, or `highways`; may retain `peaks`, but automatic peak seeding and manual peak refresh must ignore them |

The preflight schema must validate every path-bearing field (`tasmap.catalog`, `naturalFeatures.catalog`, `demSources`, regional `peaks`, `highways`, and `poly`, basemap `coveragePoly`, and the polygon manifest) and aggregate all path failures. `demSources` is an object with exactly `elvisRuntime`, `thelist25m`, and `copernicus`, each a required safe store-relative path. Route elevation for a route entirely within Tasmania uses only `elvisRuntime`; an absent, unreadable, or malformed ELVIS source is a Mapping-store failure and must not fall back to `thelist25m`. Routes not entirely within Tasmania have no runtime elevation source. `thelist25m` remains available to its separately named maintainer workflows but is not a route-elevation fallback. `routingCoverages` is an object with exactly `tasmania` and `northeast-alps`, each requiring a non-empty `displayName`; its source membership is derived from regional `routingCoverage` values, with Tasmania containing only `tasmania` and Northeast Alps containing exactly `fvg`, `veneto`, and `slovenia`. Unknown or malformed metadata entries are structural failures reported with JSON Pointers. Basemap entries require `key`, `name`, `tileUrl`, and `attribution`; `maxZoom` and `coveragePoly` are optional. Build the immutable startup catalog's required regional and coverage-polygon geometry from a versioned cache in the macOS application-support directory. `MappingCatalogCache.schemaVersion` is an app-owned persisted integer, not a Mapping data manifest field; increment it whenever cached geometry's serialized model or parsing semantics become incompatible. Reuse a cache entry only when its `schemaVersion`, hash of the validated Mapping data manifest, and each source polygon's relative path, size, modified timestamp, and content hash match the preflighted store; parse every missing, changed, or corrupt cache entry before ready and replace it after a successful parse.
