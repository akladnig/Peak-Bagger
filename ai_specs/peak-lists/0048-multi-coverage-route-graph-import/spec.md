## Problem

The app's route-graph importer still expects one obsolete `assets/highway.json` input and one singleton active graph. It cannot import the available FVG, Veneto, and Slovenia highway assets, preserve separate routing data sets, select a data set for a route, or isolate one coverage's import failure from another. This prevents Northeast Alps walking-route planning and road-target selection for the existing driving-time flow.

## Proposed Outcome

Import bundled highway assets as independent routing coverages. Tasmania remains available as its own coverage, while FVG, Veneto, and Slovenia are imported as the cross-border Northeast Alps routing coverage. Persist a route-graph manifest per coverage, select a coverage from the stored graph footprint for each route request, and retain OpenRouteService as the source of driving distance and duration.

## User Stories

1. As a hiker planning in FVG, Veneto, or Slovenia, I can create a walking route using the Northeast Alps graph, including routes that cross its source-region boundaries.
2. As a map user, I can tap an eligible road in a ready coverage and request the existing OpenRouteService driving-time calculation.
3. As a user with existing routing data, I keep using ready coverages when another coverage is importing or fails to refresh.
4. As a user, I receive a clear loading or failure state for the specific coverage needed by my route or driving-time action and can retry without losing my route draft.
5. As a maintainer, I can declare graph inputs through the region manifest and refresh every bundled coverage without stale legacy asset references breaking the operation.

## Requirements

1. Treat a routing coverage as one or more canonical manifest source regions imported into one route graph. Support the initial `tasmania` coverage from `tasmania` and the `northeast-alps` coverage from `fvg`, `veneto`, and `slovenia`. The Northeast Alps graph must combine all three inputs so graph-backed route planning may cross their source-region boundaries. Each graph-backed planned route segment and loop closure is eligible only when both endpoints select the same coverage; do not silently route one segment with incomplete data. A saved multi-point route may contain independently planned valid segments from different coverages. [L1] [L2]
2. Make `assets/region_manifest.json` the sole source of routing-coverage definitions, membership, and highway asset paths. Its top-level `routingCoverages` object maps each coverage key to an object with a required `displayName`: `tasmania` displays as `Tasmania` and `northeast-alps` displays as `Northeast Alps`. Its JSON member order is canonical: `tasmania` precedes `northeast-alps`, and the resolver must preserve that declaration order rather than sorting coverage keys. Use it for coverage bootstrap, refresh outcomes, and `<names>` substitution. `routingCoverages` is the sole non-region top-level entry: update the manifest catalog generator and manifest-derived tests to ignore it while preserving their existing region-entry contract, then regenerate and check in `lib/generated/region_manifest_catalog.g.dart`. Use `routingCoverage: "tasmania"` for Tasmania and `routingCoverage: "northeast-alps"` for FVG, Veneto, and Slovenia. Reject a source-region `routingCoverage` value that has no coverage definition. Import only non-composite source regions with a `routingCoverage` value. Composite and legacy entries without that value are excluded even if they retain a `highways` declaration. [L6]

   Every manifest consumer that enumerates regions, including the generated catalog tool, peak-region startup importer, route-graph peak-list generator, fingerprint tools, and manifest-derived tests, must skip only the exact reserved top-level key `routingCoverages` before applying region validation, seedability, priority, polygon, peak, or highway logic. Reject any other non-region top-level key. `routingCoverages` must not appear in generated region catalogs, peak imports, fingerprint results, or supported route-graph peak-list regions.
3. Replace the `RouteGraphImportService` default single-file `assets/highway.json` input with manifest-resolved coverage inputs. Do not retain a fallback to, reference to, or bundled dependency on `assets/highway.json`. Every configured highway asset must decode to an Overpass JSON object containing an `elements` array; fail that coverage import if its top-level shape is invalid. A normalized source asset path is an already-canonical Flutter asset key: it begins with `assets/`, uses `/` separators only, has no leading or trailing `/`, and contains no empty, `.` or `..` path segments. Reject a non-canonical value rather than rewriting it. Each coverage source hash is SHA-256 of UTF-8 canonical JSON with recursively lexically sorted object keys and preserved list order. Its payload contains the `routingCoverageKey` and ordered source regions; each source region contains its key, parsed priority segments, and normalized source asset paths in lexical order; each source asset contains its normalized path and decoded Overpass object in canonical JSON form, preserving `elements` order. Exclude `displayName` and schema version from the hash: a display-name change does not re-import graph data and schema version independently requires re-import. Order source regions by their parsed segmented manifest priority, rejecting a missing, malformed, or duplicate priority within a coverage; then order normalized source asset paths lexically with Dart `String.compareTo`, preserve each source `elements` array's element order, and use each accepted path unchanged for asset loading and hashing. Merge decoded source elements in that source-region, source-path, then source-element order. Deduplicate elements by their `(type, id)` OSM identity when their recursively key-sorted canonical JSON values are equal; fail that coverage import before child rows are written when two elements with the same identity differ. An accepted route-graph way is a `way` with an integer `id`, a `tags` object with a present `highway`, no `area: "yes"` or `place: "square"` exclusion, and an ordered `nodes` list resolving to at least two valid node elements with integer IDs and finite latitude and longitude coordinates. Only accepted ways may create chunks, way-index rows, or trail-display rows, or contribute to the activation count. [L3] [L6]
4. Before the first multi-coverage bootstrap, atomically delete the legacy singleton route-graph manifest and every child row in its active and stale generations; do not infer a routing coverage for legacy data. Then bootstrap Tasmania before Northeast Alps so a successfully imported Tasmania coverage remains usable if Northeast Alps fails. Bootstrap every bundled routing coverage sequentially in the background on first launch and re-import a coverage when its hash or schema version changes. Reject a candidate with no prepared chunks or no accepted route-graph ways before activation, treating it as a failed import rather than a ready coverage. Maintain independent per-coverage serving readiness: a coverage with an active generation remains usable while its replacement imports or after that replacement fails; only a coverage with no active generation is unavailable. [L5]

   Legacy data is only the pre-migration singleton manifest with primary key `RouteGraphManifest.manifestId` and a missing or empty persisted `routingCoverageKey`; never identify a legacy manifest by an inferred coverage. Persist a multi-coverage-migration-complete marker separately from coverage manifests. Before reserving any multi-coverage generation, one write transaction deletes that singleton, all three child-row types, and writes the marker. If that transaction fails, it rolls back completely and is retried; if the marker is already set, cleanup is a no-op. No coverage import may begin in the cleanup transaction.

   Bootstrap and refresh are batches. After ordered coverage definitions resolve successfully, attempt every coverage in definition order and catch a coverage-scoped load, decode, validation, preparation, or persistence failure before continuing to the next coverage. Bootstrap returns the same ordered per-coverage outcome list as refresh and does not fail the batch because one coverage fails. A hash/schema-match reuse returns `refreshed`, reports the active generation's element count, and creates no generation. A manifest-resolution failure is a batch configuration failure: start no coverage imports and expose a separate sanitized batch error.
5. Resolve graph-backed `Snap to Trail` and `Route to Peak` planning and local road-hit queries to the one coverage whose persisted active `RouteGraphChunk` footprint contains the relevant endpoint or target. A point matches a coverage when it is within at least one inclusive active chunk bound with no additional selection buffer; multiple matching chunks in one coverage count once. A graph-backed planned route segment or loop closure is eligible only when each endpoint matches exactly one active coverage and those coverage keys are equal. A road target is eligible only when it matches exactly one active coverage. Keep existing `Straight Line` route behavior everywhere. When graph-backed endpoint eligibility fails, preserve the pre-operation draft, add no segment or loop closure, show the applicable coverage message, and do not invoke the ordinary off-track or no-path straight-line fallback; retain that fallback only after a valid same-coverage graph request returns off-track or no-path. After endpoint or target selection, keep existing buffered viewport and route-payload queries. The trail overlay renders trail-display chunks from every ready active coverage whose chunks intersect its buffered viewport, omits coverages without an active generation, and continues rendering an active generation while its replacement imports or fails. Use stored chunk bounds rather than manifest polygons for active selection. [L7]
6. Preserve the existing OpenRouteService request and API-key behavior as the online authority for driving distance and duration. The local graph is used to find eligible road targets and to plan local walking routes; do not introduce local car-routing, speed, turn-restriction, or access-time calculations. [L4]
7. Coverage definitions provide the canonical display names `Tasmania` and `Northeast Alps`; use those names wherever this requirement refers to `<coverage>`. Persist a lightweight per-coverage footprint while preparing an import, independently of its active graph generation. Derive it from the inclusive bounds of every decodable source-element coordinate before accepted-way filtering. Retain the latest successfully derived footprint after a failed refresh. When no stored derived footprint exists, seed the persisted unavailable footprint from the union of member source-region coverage polygons. When neither source supplies a footprint, classify the operation as outside coverage. Use unavailable footprints only to identify a configured coverage with no active generation for unavailable-coverage messaging; never use them to select an active graph, road target, or route payload. An exact same-key active-coverage match takes precedence even if unavailable coverage footprints also contain the endpoints. Otherwise, show loading or failed messaging only when both endpoints of a graph-backed planned segment or loop closure each match exactly one identical unavailable coverage footprint; endpoints that match different unavailable coverages, or no identical unavailable coverage, use the outside-coverage message. When a planning operation matches a loading coverage with no active generation, preserve its draft and show `Routing data for <coverage> is still loading.` When that coverage becomes ready, retain the draft, replace the loading state with a `Retry` action, and replan the affected operation only when the user taps it. When it matches a failed coverage with no active generation, preserve the draft and show `Routing data for <coverage> is unavailable. Use Refresh Route Graph to retry.` When either endpoint of a graph-backed planned segment or loop closure does not match exactly one active coverage with the same key and no unavailable coverage footprint identifies both endpoints, preserve the draft, show `This route is outside a single available routing coverage.`, and do not offer Retry. Independently planned valid segments in a multi-point draft may select different coverages. Do not offer driving-time actions for road targets that do not match exactly one active coverage, including targets in coverages with no active generation. [L8]
   Resolve a road target's coverage before hit testing. Enable its driving-time action only when the target matches exactly one active coverage. When it matches exactly one unavailable loading or failed coverage, disable the action and show the corresponding exact `Routing data for <coverage> is still loading.` or `Routing data for <coverage> is unavailable. Use Refresh Route Graph to retry.` message. When it does not match exactly one active or unavailable coverage, disable the action and show `Driving time is unavailable outside routing coverage.` Do not invoke OpenRouteService unless the target matches exactly one active coverage.

8. Make Refresh Route Graph refresh every configured bundled coverage sequentially. Replacement is atomic per coverage: commit a completed replacement only after its complete next generation is prepared, keep a previous valid generation when its refresh fails, and commit other successful coverage refreshes. Return an ordered per-coverage outcome list containing the `routingCoverageKey`, canonical `displayName`, status (`refreshed` or `failed`), element count for successes, and a sanitized error for failures. Order outcomes by routing-coverage definition order: Tasmania, then Northeast Alps. For mixed outcomes, show the exact dialog title `Route Graph Refresh Partially Completed` with body lines `Refreshed: <names>.` and `Failed: <names>.` Keep `Route Graph Refreshed` for all-success and `Route Graph Refresh Failed` for all-failed outcomes, and name each affected coverage or coverages. A failed replacement that retains an active generation remains a failed refresh outcome while its coverage remains usable. [L5] [L9]

    For all-success outcomes, the `Route Graph Refreshed` dialog body is exactly `Refreshed: <names>.` For all-failed outcomes, the `Route Graph Refresh Failed` dialog body is exactly `Failed: <names>.`

## Contract Clarifications

1. A routing-coverage definition resolver failure is a typed batch-configuration failure, not a per-coverage failure. Bootstrap and Refresh Route Graph return a tagged batch result: either an ordered completed per-coverage outcome list or a configuration failure carrying one sanitized message. All prior ordered outcome-list contracts apply only to the completed result. On a configuration failure, start no imports, return no per-coverage outcomes, and leave every persisted active generation, coverage serving readiness, and coverage import state unchanged. Bootstrap records and exposes the global configuration failure without a modal dialog. A Settings refresh shows an exact dialog title `Route Graph Configuration Error` with body `Route graph configuration is invalid. Refresh did not start.`
2. All bootstrap and refresh callers join one app-owned queued or running batch instead of enqueueing a duplicate batch. A confirmed Settings Refresh Route Graph request while bootstrap is queued or running joins that bootstrap batch, returns its same tagged batch result, and never queues a post-bootstrap refresh. A later newly confirmed Settings refresh may start a new batch after bootstrap completes. A Settings Refresh Route Graph confirmation canceled by the user creates no request. A confirmed batch continues after Settings is disposed; only the initiating Settings screen, when still mounted, may show its completion dialog, and joined callers do not show duplicate dialogs.
3. Substitute `<names>` in refresh dialog bodies with canonical display names in routing-coverage definition order, joined by `, `; the initial all-success value is `Tasmania, Northeast Alps`. Sanitized per-coverage errors remain in the returned outcome for diagnostics and logging but are never rendered in a refresh result dialog. When a retained route draft's loading coverage becomes ready, replace the loading message with exactly `Routing data for <coverage> is ready. Retry to plan this route.` and a `Retry` action; do not replan until that action is tapped.
4. Canonical source JSON accepts only standard JSON `null`, booleans, strings, finite numbers, lists, and string-keyed objects. Sort every object by Dart `String.compareTo` order and preserve list order. Normalize each finite integral `double` to an integer before using Dart `jsonEncode`; therefore semantically equivalent `1` and `1.0` produce the same canonical hash. Reject non-finite or otherwise unsupported values before hashing.
5. Coverage-specific route feedback and refresh dialogs must wrap without clipping. At a 360x800 logical-pixel surface with 200% text scale, the feedback, `Retry`, and enabled or disabled driving-time actions remain visible and operable. Semantics expose each coverage-status message and the reason a driving-time action is disabled.
6. The route-graph schema version for this multi-coverage migration is exactly `route-graph-v5`. Each coverage source hash is SHA-256 of the UTF-8 canonical JSON form of exactly this payload shape:

   ```json
   {
     "routingCoverageKey": "tasmania",
     "sourceRegions": [
       {
         "key": "tasmania",
         "prioritySegments": [1, 1],
         "sourceAssets": [
           {
             "path": "assets/highways/tasmania-highways.json",
             "overpass": {
               "elements": []
             }
           }
         ]
       }
     ]
   }
   ```

   `sourceRegions` uses the manifest-priority order and `sourceAssets` uses the normalized path order required above. `prioritySegments` is the ordered list of parsed integer priority segments. `overpass` is the decoded source Overpass object. Canonical JSON recursively sorts every object key with Dart `String.compareTo` and preserves every list's order. The hash excludes `displayName` and the schema version; any future change to this payload shape requires a schema-version increment.
7. A coverage's import state is exactly `queued`, `importing`, `ready`, or `failed`, separately from whether it has an active generation. After coverage definitions resolve successfully, create or retain each coverage's unavailable footprint and mark every coverage without an active generation `queued`; then transition coverage imports in definition order from `queued` to `importing`. For a `queued` or `importing` coverage with no active generation, use the exact loading feedback `Routing data for <coverage> is still loading.` For a `failed` coverage with no active generation, use the exact failed feedback required above. For a coverage with an active generation, continue using that generation in `queued`, `importing`, and `failed` states without unavailable feedback. A configuration failure leaves all coverage states and unavailable footprints unchanged. A retained route draft receives the ready-to-Retry transition only when the coverage that originally produced its loading feedback first reaches `ready`.
8. Persist each unavailable footprint as an ordered union of inclusive latitude/longitude bounds. The derived footprint contains one bound per configured source asset, built from every finite numeric `lat` and `lon` pair on decoded `node` elements before accepted-way filtering; a source asset with no such coordinates contributes no bound. When no derived footprint exists, seed one bound per member source-region coverage polygon using that polygon's inclusive latitude/longitude envelope. The persisted bound order is source-region manifest priority, normalized source-path lexical order, then declared polygon order. A point matches an unavailable footprint when it is within at least one bound inclusively; multiple matching bounds for the same coverage count once. This bound representation is the required meaning of the source-region coverage-polygon union in the unavailable-footprint fallback.
9. A route `Retry` is bound to the route operation type, its original endpoints or peak target, and the route draft revision that produced loading feedback. Any route-draft revision change invalidates that `Retry` and removes its ready-to-Retry feedback; the user must initiate a new route operation from the edited draft. Before a valid `Retry` invokes the route planner, re-evaluate active-coverage eligibility for its bound endpoints; on failure, preserve the draft, add no segment or loop closure, show the applicable current coverage feedback, and do not invoke the route planner or straight-line fallback. Before a driving-time action invokes OpenRouteService, re-evaluate the bound road target against active coverage. If it no longer matches exactly one active coverage, do not invoke OpenRouteService and update the action to the exact current loading, failed, or outside-coverage disabled message required above.

## Technical Decisions

1. Replace the singleton `RouteGraphManifest.manifestId` model with one persisted Route-graph manifest per routing coverage. Store an indexed, unique `routingCoverageKey`, the active generation, aggregate source hash, schema version, import timestamp, counts, readiness/error state, and the coverage's ordered source-region keys for provenance. [L1] [L10]

    Persist a singleton route-graph import metadata record separately from `RouteGraphManifest` so it cannot be confused with a coverage's readiness or provenance. It contains the multi-coverage-migration-complete marker and a durable `lastReservedGeneration` counter.
2. Reserve route-graph generation IDs globally across all coverages in a short storage transaction before preparing child rows by incrementing and persisting the metadata record's `lastReservedGeneration`; the returned value is the generation ID. The counter is never decremented or reused, including after a failed import or app restart, so a failed import may leave an unused reserved ID. Keep `RouteGraphChunk`, `RouteGraphWayIndex`, and `RouteGraphTrailDisplayChunk` associated through that globally unique generation and their existing record keys; do not duplicate a `region` or coverage key on every child entity. Activate the fully prepared generation atomically per coverage. Update ObjectBox schema generation, storage queries, repository caches, and in-memory test storage accordingly. [L10]
3. Extend the repository, store, query service, route planner client, trail service, road-hit service, readiness provider, and refresh result contracts to select and report routing coverages rather than one app-wide active graph. Replace app-wide readiness consumers in map and Settings controls with a coverage-selection readiness lookup; no coverage's import state may disable another coverage's ready graph. Model serving readiness separately from import state: an active generation remains ready while a replacement imports or after a replacement failure, and import state retains the refresh error. Cache keys must include the selected coverage generation so one coverage cannot serve stale geometry or indexes for another; trail-overlay cache keys include ordered `(routingCoverageKey, activeGeneration, chunkKey)` values. [L5] [L7] [L8] [L10]
4. Keep manifest parsing and asset loading behind injectable boundaries. Add a coverage-definition resolver that reads top-level `routingCoverages` display names in their declared JSON member order, groups non-composite manifest regions by `routingCoverage`, validates each declared source asset's canonical Flutter asset key and imported Overpass shape, and yields deterministic coverage, source-region, and source-path ordering. It must expose the deterministic decoded-element merge and same-identity conflict failure required above. During preparation, derive and persist a lightweight per-coverage footprint for unavailable-coverage classification without activating graph rows. Do not make absent legacy assets outside configured coverage membership fatal. [L3] [L6]
5. Preserve existing Riverpod and route-draft state conventions. Coverage imports and refreshes must not create unowned controllers, streams, or timers; asynchronous completions must not update unmounted UI. Continue logging import, refresh, and OpenRouteService failures without exposing secrets or API-key values. [L4] [L5] [L8]
6. Use one app-owned import coordinator to queue and serialize all coverage bootstrap and Settings refresh work. A manual refresh requested during bootstrap joins that bootstrap batch rather than running concurrently or queuing a follow-up refresh; the coordinator processes each coverage sequentially and preserves per-coverage atomic replacement and readiness. Expose injectable per-coverage import status and completion events so widget and robot tests can deterministically control bootstrap, queued refresh, and loading-to-Retry transitions. [L5] [L9] [L10]

   Provide the coordinator through Riverpod with injectable `bootstrap`, `refreshAll`, per-coverage state lookup, and per-coverage completion events. Tests must be able to hold and complete an individual coverage import without timers, isolates, or real assets.

## Out of Scope

1. Implementing a local car-routing engine, including road speeds, turn restrictions, access-time rules, or offline driving durations. [L4]
2. Changing the existing OpenRouteService API-key storage or replacing its distance/duration response contract. [L4]
3. Adding routing coverage membership to composite or legacy manifest entries that are not explicitly configured with `routingCoverage`. [L6]
4. Automatically routing one planned segment or loop closure across separate routing coverages, or silently falling back to a different coverage. This does not exclude a saved multi-point route whose independently planned valid segments use different coverages. [L2] [L7]
