## Problem

The repo already has Tasmania DEM-backed behavior in two places, but those paths are inconsistent with the intended ELVIS adoption. Flutter route elevation sampling still relies on bundled DEM assets and currently treats `ELVIS` as a bundled-asset alias, while Tasmania `Local Topo` rebuilds still expect higher-detail DEM input only as a generic local override. There is no repo-owned workflow that validates the full raw ELVIS Tasmania source, derives stable consumer artifacts from it, and makes both the Flutter app and `Local Topo` rebuilds use ELVIS as the Tasmania source of truth. [L1] [L2] [L5] [L10] [L11]

## Proposed Outcome

Add a maintainer-owned ELVIS derivation workflow that treats `/Volumes/Media/Elvis/tas-elvis` as the canonical raw Tasmania `ELVIS DEM`, validates that frozen source against a committed completeness manifest, and produces two external statewide GeoTIFF derivatives under the repo's Tasmania DEM root: a `10m` `ELVIS runtime DEM` for Tasmania Flutter route elevation sampling and a `5m` `ELVIS topo DEM` for Tasmania `Local Topo` rebuilds. The ELVIS-specific Tasmania DEM-root resolver uses `~/Documents/Bushwalking/DEM/Tasmania/` when `~/Documents/Bushwalking` exists, otherwise `$HOME/DEM/Tasmania/`, and fails clearly if `HOME` is unavailable without changing the repo's broader Bushwalking-root helper semantics for unrelated features. The workflow is exposed through a root shell wrapper `./elvis_dem.sh` backed by `tool/elvis_dem.dart`, while the Flutter app and `Local Topo` shell scripts consume the prepared artifacts from fixed canonical paths and fail clearly when those artifacts are missing or invalid. Tasmania stops using the bundled `theLIST 25m DEM` as its normal runtime source after ELVIS adoption, and non-Tasmania regions resolve to no runtime DEM in this slice. [L1] [L2] [L3] [L5] [L6] [L7] [L8] [L9] [L10] [L11] [L13] [L16] [L18] [L19] [L20] [L22] [L23] [L24]

## User Stories

1. As a maintainer, I can run a shell command that validates the full completed ELVIS Tasmania source against a frozen manifest and then build stable statewide runtime and topo DEM derivatives without using `dart run` manually. [L3] [L12] [L13] [L17] [L18] [L19]
2. As a maintainer, I keep the raw `260 GB` ELVIS source at `/Volumes/Media/Elvis/tas-elvis`, avoid duplicating it under the Bushwalking root, and commit only the small tool and manifest artifacts needed to make the workflow reproducible. [L7] [L14] [L15] [L20] [L25] [L26]
3. As a Flutter route-planning user, Tasmania route elevation sampling uses the prepared `ELVIS runtime DEM` from a fixed maintainer-managed path with no new Settings UI for choosing a DEM file, while non-Tasmania routes show `Elevation unavailable for this region` instead of trying to use a Tasmania DEM. [L5] [L9] [L16] [L22]
4. As a `Local Topo` maintainer, routine Tasmania refresh scripts stay shell-script entrypoints that consume the prepared `ELVIS topo DEM` by default, allow any alternate DEM only when I opt into it explicitly via a flag, continue owning contour and terrain-relief generation, and fail with clear maintainer instructions when the selected DEM input is missing or invalid. [L8] [L11] [L23] [L24]
5. As a repo maintainer, ELVIS becomes the required Tasmania elevation source of truth for both Flutter elevation sampling and `Local Topo`, rather than a placeholder alias or an optional partial-coverage source. [L1] [L3] [L4] [L6] [L10] [L22]

## Requirements

1. Treat `ELVIS DEM` as the canonical higher-detail Tasmania DEM input for this repo. The canonical raw source root is `/Volumes/Media/Elvis/tas-elvis`, and both Flutter elevation sampling and Tasmania `Local Topo` rebuild workflows must use ELVIS through repo-managed derived artifacts rather than direct runtime reads from the raw source tree. [L1] [L4] [L7]
2. ELVIS must not be used until the full Tasmania raw dataset is present. The derivation workflow must refuse to build runtime or topo artifacts until the canonical raw source validates successfully against the frozen completeness manifest. Partial ELVIS coverage is not a supported steady-state mode for this slice. [L3] [L12] [L14] [L15] [L26]
3. Keep one external ELVIS raw source tree, but generate separate derived artifacts per consumer workflow. The repo must not collapse Flutter/runtime and `Local Topo` needs into one shared statewide artifact. [L2] [L8] [L9]
4. Scope ELVIS adoption in this slice to Tasmania `Local Topo` rebuilds, Flutter route elevation sampling, and shared repo DEM tooling. Do not include retroactive stored peak-elevation rewrites or non-Tasmania elevation workflows in this Spec. [L4]
5. The ELVIS workflow must be implemented as a Dart maintainer CLI at `tool/elvis_dem.dart` plus a root shell wrapper `./elvis_dem.sh`. The wrapper must follow the repo's existing auto-build macOS maintainer-tool pattern so the tool can be run as a shell script rather than via `dart run`. [L11] [L13]
6. `./elvis_dem.sh` must expose explicit subcommands: `bootstrap-manifest`, `validate-source`, `build-runtime`, `build-topo`, and `build-all`. Invoking the wrapper without a subcommand must print help and exit non-zero. `bootstrap-manifest` must print the raw source path it used and the manifest path it wrote. `validate-source`, `build-runtime`, `build-topo`, and `build-all` must print the raw source path they validated or used, the generated artifact path or paths, and the machine-readable report path they wrote. Any validation or build error must exit non-zero. [L12] [L13] [L17]
7. The raw ELVIS source must remain at `/Volumes/Media/Elvis/tas-elvis`. This slice targets the existing macOS app and maintainer workflow only. Do not create a second full-data mirror under `~/Documents/Bushwalking`. The ELVIS CLI, app runtime DEM resolution, and Tasmania `Local Topo` DEM consumers must use a dedicated Tasmania DEM-root resolver for this slice. That resolver must place generated artifacts under `~/Documents/Bushwalking/DEM/Tasmania/` when `~/Documents/Bushwalking` exists, otherwise under `$HOME/DEM/Tasmania/`. ELVIS path resolution must stop at `$HOME`; if `HOME` is unavailable, commands and runtime consumers must fail clearly rather than falling back to another location. This slice must not change the repo's broader `resolveBushwalkingRoot()` behavior for unrelated features. [L7]
8. Generate exactly two stable statewide ELVIS-derived DEM artifacts under the resolved Tasmania DEM root from requirement 7:
   - `<tasmania-dem-root>/elvis_runtime_10m.tif`
   - `<tasmania-dem-root>/elvis_topo/elvis_topo_5m.tif`

   Each artifact is a single statewide GeoTIFF, not a multi-file regional index contract. Internal VRTs or temp files may exist during derivation, but consumers must depend on these stable GeoTIFF outputs only. [L8] [L9] [L18] [L19]
9. The `ELVIS runtime DEM` must be a `10m` external statewide GeoTIFF derived from the full ELVIS source and intended for Flutter elevation sampling only. The Flutter app must not point at the raw ELVIS tile tree and must not require that statewide ELVIS be bundled into the app package. [L5] [L8] [L9]
10. The `ELVIS topo DEM` must be a separate `5m` external statewide GeoTIFF derived from the full ELVIS source and intended for Tasmania `Local Topo` contour and terrain-relief build workflows only. It must be written in `EPSG:28355` so the existing Tasmania `Local Topo` contour and terrain-relief workflow can consume it without introducing a new source-SRS detection contract in this slice. For the same reason, every Tasmania `Local Topo` DEM source supported in this slice must be consumed as an `EPSG:28355` GeoTIFF: `elvis-topo`, `thelist`, and `copernicus` resolve to maintainer-managed configured GeoTIFFs already in `EPSG:28355`, and `--dem-source=custom` requires `--dem-path` to point at an absolute-path readable GeoTIFF already in `EPSG:28355`. This slice must not add runtime CRS inspection or alternate-source reprojection behavior for `Local Topo` DEM selection. The `ELVIS runtime DEM` and `ELVIS topo DEM` must not be treated as interchangeable artifacts. [L8] [L9]
11. The current code contract that treats `ELVIS` as a bundled asset alias must be removed. Tasmania runtime elevation behavior must resolve ELVIS to the fixed external `ELVIS runtime DEM` path, `theLIST 25m DEM` must stop being the normal Tasmania runtime source, and non-Tasmania runtime elevation behavior must resolve to `none` in this slice rather than to a bundled Tasmania DEM or `Copernicus GLO-30`. `Copernicus GLO-30` remains a distinct future source rather than an ELVIS stand-in. [L10]
12. The Flutter app must resolve the Tasmania `ELVIS runtime DEM` from a fixed maintainer-managed path and must not add a Settings UI or other user-facing file picker for DEM selection in this slice. Before any dataset open or elevation sampling work, all app elevation workflows in this slice must resolve the route DEM using the repo's existing region-classification helper or an equivalent shared seam rather than duplicating Tasmania-only bounds logic. If every route point resolves within Tasmania, use the fixed external `ELVIS runtime DEM`. Otherwise resolve to `dem=none`. Non-Tasmania routes must not attempt dataset open or sampling work. When the route region resolves to `none`, the interactive route elevation UI must show the exact message `Elevation unavailable for this region`, replacing the current `No elevation data yet` message for that case. [L6] [L16] [L22]
13. After ELVIS adoption, Tasmania runtime elevation and Tasmania `Local Topo` rebuild workflows must fail fast when their required selected DEM artifacts are missing or invalid. Silent fallback to `theLIST 25m DEM` is not allowed as steady-state post-adoption behavior. When the resolved region is Tasmania but the fixed `ELVIS runtime DEM` is missing, unreadable, or cannot be opened, the interactive route elevation UI must show the exact message `Tasmania elevation data is unavailable on this device` in both the route elevation summary error surface and the elevation profile chart error state. Non-interactive elevation workflows that already behave best-effort, such as imported-route enrichment, route-save point elevation sampling, and GPX route export elevation sampling, may remain best-effort, but they must first short-circuit when the resolved region DEM is `none` rather than relying on swallowed dataset-open failures as control flow. [L6] [L22]
14. The completeness manifest is a frozen immutable source contract rather than a normal refresh workflow artifact. Commit it to `tool/elvis_dem_manifest.json` and use it for all routine ELVIS validation. Unexpected raw-source changes must fail validation rather than trigger automatic manifest updates or adaptive source-refresh behavior. [L12] [L14] [L15]
15. The completeness manifest must validate only ELVIS DEM payload files, not transient OS metadata such as `.DS_Store`. Ignore known transient metadata files during manifest bootstrap and normal validation. [L25]
16. The completeness manifest must enumerate every expected payload file explicitly. For each expected file, store at least its relative path under `/Volumes/Media/Elvis/tas-elvis`, byte size, and a `sha256` checksum encoded as lowercase hexadecimal over the file's raw bytes. The manifest must also store manifest-level totals such as file count and total bytes. Wildcard or pattern-based expectations are not acceptable for this frozen contract. [L12] [L15] [L26]
17. `bootstrap-manifest` is a one-time maintainer command used only after the full source is present. Normal commands such as `validate-source`, `build-runtime`, `build-topo`, and `build-all` must refuse to proceed unless the committed frozen completeness manifest at `tool/elvis_dem_manifest.json` already exists and passes validation rules. [L12] [L17]
18. The derivation workflow must write machine-readable validation and build reports under `elvis_reports/` within the resolved Tasmania DEM root, with timestamped filenames in UTC shaped as `<command>-YYYYMMDDTHHMMSSZ.report.json`. This report contract applies to `validate-source`, `build-runtime`, `build-topo`, and `build-all`; `bootstrap-manifest` writes the frozen manifest file itself rather than a timestamped report under `elvis_reports/`. Generated DEM artifacts must also have fixed sidecar metadata files beside the GeoTIFF outputs: `elvis_runtime_10m.metadata.json` beside `elvis_runtime_10m.tif`, and `elvis_topo_5m.metadata.json` beside `elvis_topo_5m.tif`. Sidecars must record provenance such as source completeness state, generation time, and key derivation parameters. The small report and metadata schemas may be committed as examples or contracts, but generated local reports themselves must remain out of git. [L12] [L18] [L20]
19. Commit only the ELVIS tooling and small manifest artifacts needed to make the workflow reproducible. Do not commit generated statewide GeoTIFFs, VRTs, caches, temp directories, or local validation or build reports. [L20]
20. `Local Topo` refresh entrypoints must remain shell-script entrypoints. They must not derive ELVIS artifacts inline, must not require `dart run`, and must not rescan the raw `260 GB` source during normal refresh operations. Instead, they must accept an explicit `--dem-source` flag whose supported values are exactly `elvis-topo`, `thelist`, `copernicus`, and `custom`. The default value is `elvis-topo`. When `--dem-source=custom` is used, the caller must also provide `--dem-path` as an absolute path to a readable `EPSG:28355` GeoTIFF. For named sources, the scripts must resolve the selected DEM from its maintainer-managed configured location as a readable `EPSG:28355` GeoTIFF. Rebuild scripts must consume only the selected DEM for a given rebuild and validate that the selected input exists and is readable. Automatic DEM selection or fallback to another DEM is not allowed. This slice must not add source-CRS detection or alternate-source reprojection behavior to make other DEM coordinate systems work. If the selected `elvis-topo` input is missing, the scripts must fail fast with a clear maintainer command such as `./elvis_dem.sh build-topo`. [L11] [L13] [L24]
21. Update Tasmania `Local Topo` maintainer-facing usage docs to match the post-adoption DEM contract. At minimum, `local_topo/tasmania/README.md` and any rebuild-script help or usage output touched by this slice must stop describing DEM auto-selection or fallback behavior and must document the explicit `--dem-source` contract instead. [L11] [L24]
22. The ELVIS CLI stops at producing the `ELVIS runtime DEM` and `ELVIS topo DEM`. Tasmania `Local Topo` rebuild scripts remain responsible for contour generation, contour GeoJSON or `MBTiles` generation, terrain relief shading, and any topo-specific `source-metadata.json` written beside prerendered tile output. [L23] [L24]

## Technical Decisions

1. Reuse the repo's canonical Bushwalking-root local-data convention for generated ELVIS artifacts while keeping the raw source outside that tree, but make the ELVIS-specific fallback explicit through a dedicated Tasmania DEM-root resolver: use `~/Documents/Bushwalking` when present, otherwise `$HOME`, and fail if `HOME` is unavailable. This avoids duplicating the full ELVIS dataset while preserving stable generated-file locations for repo consumers without changing the repo-wide Bushwalking-root helper used by unrelated features. [L7]
2. Split ELVIS into two derived statewide consumer artifacts instead of one shared output: a `10m` `ELVIS runtime DEM` for Flutter elevation sampling and a `5m` `ELVIS topo DEM` for `Local Topo` cartography workflows. This keeps app-size and runtime concerns separate from contour and hillshade quality concerns. [L2] [L8] [L9]
3. Keep ELVIS derivation as a dedicated maintainer workflow owned by `tool/elvis_dem.dart` and `./elvis_dem.sh`, while `Local Topo` refresh remains a shell-script rebuild workflow that consumes the prepared topo artifact. [L11] [L13] [L24]
4. Treat the raw ELVIS source as a frozen immutable snapshot enforced by a committed explicit-file completeness manifest with checksums and totals, while ignoring OS-transient files such as `.DS_Store`. This turns “the full `260 GB` source is present” into a reproducible validation contract instead of a loose directory-size heuristic. [L12] [L14] [L15] [L25] [L26]
5. Preserve a fixed maintainer-managed DEM path for Flutter rather than adding a user-configurable DEM setting. All app elevation workflows in this slice use the repo's existing region-classification helper or an equivalent shared seam to resolve the DEM before any dataset open. If every route point resolves within Tasmania, use the external `ELVIS runtime DEM`; otherwise resolve to `dem=none`. The app already has a clear maintainer-versus-user boundary for similar infrastructure contracts, and an explicit shared region-to-DEM resolver keeps the elevation contract smaller and more testable. [L16]
6. Replace the current bundled-asset ELVIS placeholder in `lib/core/constants.dart` and related runtime code so Tasmania elevation behavior matches the agreed external ELVIS contract. `theLIST 25m DEM` stops being the normal Tasmania runtime fallback after adoption, and `Copernicus GLO-30` remains reserved for a future region-specific runtime slice rather than being activated here. [L10] [L22]
7. Keep contour and terrain-relief generation in the existing Tasmania `Local Topo` rebuild seam rather than expanding the ELVIS CLI into a topo-artifact generator, but replace implicit DEM auto-selection with an explicit `--dem-source` contract supporting only `elvis-topo`, `thelist`, `copernicus`, and `custom`, defaulting to `elvis-topo`, with `custom` requiring `--dem-path`. To keep this slice aligned with the existing contour seam, every supported `Local Topo` DEM source must already be a readable `EPSG:28355` GeoTIFF rather than triggering new CRS detection or reprojection logic during source selection. This preserves current separation between source-derivation work and topo-cartography work while making DEM provenance deterministic. [L23] [L24]

## Testing Strategy

1. Add deterministic tool coverage under `test/tool/` for manifest bootstrap output, source validation success, wrong-size and checksum-mismatch failures, missing-file failures, build planning, and build-metadata output. Prefer behavior-first TDD for the validation and derivation logic. [L12] [L15] [L17] [L18] [L21] [L26]
2. Add a dedicated shell-wrapper test for the root wrapper pattern that verifies `./elvis_dem.sh` forwards subcommands and flags to the tool entrypoint using an injectable fake-binary seam, aligned with the existing wrapper-testing pattern in `test/tool/slovenia_hribi_source_peak_list_tool_test.dart`. The runner seam should verify command execution expectations without depending on the real ELVIS source. [L13] [L21]
3. Extend `local_topo/tasmania/tests/rebuild_scripts.test.mjs` so Tasmania `Local Topo` rebuild scripts prove they default to `--dem-source=elvis-topo`, honor explicit `thelist`, `copernicus`, and `custom` selection when provided, require `--dem-path` for `custom`, reject `custom` or named-source DEM inputs that are not accepted as readable `EPSG:28355` GeoTIFFs for this slice, fail clearly when the selected DEM is missing or invalid, never auto-fallback to another DEM, and do not try to rescan or rebuild from the raw ELVIS source inline. Add coverage that maintainer-facing README/help text no longer advertises DEM auto-selection or fallback behavior once this slice lands if those docs or help surfaces are updated in-code or fixture assertions. [L21] [L23] [L24]
4. Add app-side deterministic coverage for the Tasmania runtime DEM contract around `lib/core/constants.dart`, the route elevation sampler seams, and any provider or service logic that resolves the runtime DEM per region. Cover the shared region-classification seam deciding that Tasmania requires every route point to resolve within Tasmania before using the external runtime path, non-Tasmania resolving to `dem=none`, the exact `Elevation unavailable for this region` UI message, and the exact `Tasmania elevation data is unavailable on this device` message for missing or unreadable Tasmania runtime DEMs, without adding a user-facing DEM file setting. Reuse existing fake seams such as `DemAssetCache` and `DemDatasetOpener` or replace them with equivalent external-file seams as needed. [L5] [L10] [L16] [L22]
5. Keep automated coverage free of the real `260 GB` source, live mounted volumes, or generated statewide GeoTIFF dependencies. Use temp directories, fixture manifests, fake checksum inputs, fake dataset openers, and repo-local script fixtures instead. Verify that best-effort non-interactive elevation flows short-circuit before dataset open when `dem=none`, and verify timestamped report filename shape and fixed sidecar metadata paths. Robot or widget journey coverage is not required for this slice unless user-visible route elevation messaging changes materially beyond the existing elevation error seam. [L21]

## Out of Scope

1. Retroactively rewriting stored peak elevations or broadening ELVIS adoption to non-Tasmania elevation workflows. [L4]
2. Allowing partial ELVIS coverage before the full Tasmania dataset is present. [L3]
3. Adding a user-facing DEM-file chooser or Settings control for runtime DEM selection. [L16]
4. Direct runtime reads from `/Volumes/Media/Elvis/tas-elvis` by the Flutter app or by routine `Local Topo` refresh scripts. [L1] [L11]
5. Silent Tasmania fallback to `theLIST 25m DEM` after ELVIS adoption. [L6] [L22]
6. Having the ELVIS CLI generate contour artifacts, contour `MBTiles`, hillshade, or prerendered `Local Topo` tiles directly. [L23]
7. Designing a normal raw-source update or manifest-refresh workflow for ELVIS. [L14]
8. Checking the generated statewide ELVIS GeoTIFFs, VRTs, caches, or local reports into git. [L20]

## Follow-Ups

1. Remove any remaining Tasmania-specific bundled DEM asset usage once all runtime, test, and maintainer seams no longer depend on it. [L22]
2. Consider later ELVIS-backed workflows such as stored peak-elevation backfills only if a separate future request explicitly expands scope beyond route elevation sampling and `Local Topo`. [L4]
