## Problem

Maintainers need a reproducible, import-ready list of peaks from the canonical peak source CSV that lie near any route-graph way in a selected region. The current route graph indexes highway metadata in ObjectBox but does not retain the geometry required for proximity matching, and existing app exports only persisted peak lists.

## Proposed Outcome

Provide a standalone Dart CLI with a root-level macOS shell launcher. It reads the canonical 25-column peak source CSV at `~/Documents/Bushwalking/Features/peaks.csv`, resolves the selected region's highway JSON locations from `assets/region_manifest.json`, and produces one app-owned peak-list export CSV containing each peak within 50 m of an eligible route-graph-way segment.

## User Stories

1. As a maintainer, I can run the launcher without arguments to export Tasmania's route-graph-proximate peaks as an import-ready CSV.
2. As a maintainer, I can select a supported manifest region and output path explicitly, so a future region's matching list can be generated reproducibly.
3. As a maintainer, I receive actionable failures instead of a partial or misleading CSV when the selected region, peak source, or highway inputs are unavailable.

## Requirements

1. Add a testable standalone Dart entry point under `tool/` and a root-level shell launcher that builds it as a release macOS Flutter executable when its relevant sources are newer, then forwards all arguments. The launcher must establish the repository root for runtime path resolution and must rebuild when the existing executable was built for a different tool entry point. Do not implement this workflow as plain `dart run`. [L13]
2. Support `--region <manifest-key>`, `--output <path>`, `--help`/`-h`, and no positional arguments. Normalize region keys case-insensitively; default omitted `--region` to `tasmania`. Resolve a selected key's effective `highways` paths from its own non-empty declaration or, when absent, by repeatedly removing the final segment of its manifest `priority` until an ancestor with a non-empty declaration is found. Invalid syntax, unknown keys, and keys with no ancestor that declares one or more `highways` paths must write a useful error to stderr and exit `1`. [L17]
3. `--help` must describe the command, options, default `tasmania` region, default peak source path `~/Documents/Bushwalking/Features/peaks.csv`, default output convention, and list every canonical manifest key that resolves to one or more effective `highways` paths directly or through an ancestor. It exits `0` without reading the peak source or writing a file. [L15] [L16]
4. Read `assets/region_manifest.json` as the source of each selected region's effective highway paths. Resolve every listed path relative to the repository root, parse their Overpass JSON geometry, and combine their eligible ways. Do not use `RouteGraphWayIndex` as the matching source. [L3]
5. A route-graph way is an OSM `way` with a non-null `highway` tag, except one tagged `area=yes` or `place=square`; include `path`, `track`, and `footway` and do not restrict the set to roads. Highway files use Overpass top-level `node` elements with numeric IDs and finite, in-range `lat`/`lon` values plus `way.nodes` ID references. Ignore individually malformed top-level nodes. Resolve `way.nodes` as contiguous valid point runs: an unresolved or unusable reference breaks the run, and no segment may bridge across it. Skip an individual eligible way that cannot resolve at least two points in a run, but treat a file with no usable eligible segments as an invalid highway data set. [L2]
6. Read `~/Documents/Bushwalking/Features/peaks.csv` as the peak source. Require exactly these 25 CSV headers, in this order: `id`, `osmId`, `peakbaggerPid`, `name`, `altName`, `elevation`, `prominence`, `country`, `county`, `range`, `rating`, `durationMinutes`, `durationLabel`, `difficulty`, `viaFerrata`, `notes`, `latitude`, `longitude`, `region`, `gridZoneDesignator`, `mgrs100kId`, `easting`, `northing`, `verified`, and `sourceOfTruth`. Reject the entire source when any row has a missing, non-positive, or non-integer `id`; missing, zero, or non-integer `osmId`; blank `name`; non-finite or out-of-range latitude/longitude; or a `verified` value other than `true` or `false` case-insensitively. `peakbaggerPid` and `durationMinutes` may be blank, otherwise must be integers; `elevation`, `prominence`, and `rating` may be blank, otherwise must be finite. All other text fields may be blank. Invalid or blank MGRS components are valid input because the export uses the existing MGRS fallback. Any invalid row makes the source malformed and fails the run before the output is replaced. [L16]
7. Normalize each source `region` value by trimming and case-folding it before eligibility filtering and output. For a non-composite selected manifest region, eligible normalized source-region values are the selected key plus its `peakListFilterAliases`, even when its effective highway paths come from an ancestor. For a selected composite manifest region, eligible normalized source-region values are the keys and aliases of each non-composite manifest region whose non-empty effective `highways` paths are included in the selected region's effective `highways` paths. This makes `italy-nord-est` include its `fvg`, `veneto`, `trentino-alto-adige`, and `emilia-romagna` aliases, and makes `italy` include the eligible values for both Italian aggregate regions. Write the normalized matching source-region value to each output row; do not replace an administrative source region such as `fvg` with a selected aggregate key. A candidate is selected if its latitude/longitude is within or exactly at 50 m of any eligible way segment. Matching is two-dimensional only: do not require or synthesize highway elevation data. Emit each selected peak once even when it matches multiple way segments or inputs. [L1] [L14] [L16] [L17]
8. Produce exactly one app-owned export CSV. Use the existing 22-column header and value rules from `PeakListCsvExportService`, including MGRS fallback, rating and duration formatting, and lowercase boolean values. Write `1` in every `points` column. [L8]
9. Sort rows by case-insensitive peak name and then numeric `osmId`, matching the current app-owned exporter. [L9]
10. Without `--output`, write `~/Documents/Bushwalking/Peak_Lists/<canonical-region>-route-graph-peak-list.csv`. With `--output`, write exactly that file path. Require the destination parent directory to exist; do not create directories. [L6]
11. Replace an existing target atomically only after all source validation, matching, and CSV construction succeeds. Use a temporary sibling file and remove it if writing or renaming fails. On success, print the output path and matched-peak count to stdout and exit `0`. [L12]
12. When no peaks match, write a valid header-only CSV, print a zero matched-peak count, and exit `0`. [L11]
13. If the peak source is missing, unreadable, malformed, or does not have the required 25-column schema, write its path and parsing detail to stderr, exit `1`, and leave no newly written or replaced output CSV. [L16]
14. If a selected manifest-listed highway file is missing or unreadable, or its JSON cannot provide a valid highway data set, write the selected region and relevant path or parsing detail to stderr, exit `1`, and leave no newly written or replaced output CSV. [L4]

## Technical Decisions

1. Parse raw region highway files because geometry is required for segment distance calculation; `RouteGraphWayIndex` contains index metadata only and duplicates OSM ways across chunks. Resolve a selected key without `highways` by following its segmented manifest `priority` ancestors until one supplies the effective highway paths. [L3] [L17]
2. Reuse the current route-graph importer semantics for accepting OSM highway ways and the existing finite-segment geospatial approach used by peak correlation. The new matcher has no elevation criterion. [L2] [L14]
3. Load the raw manifest rather than extending the generated runtime region catalog solely for this CLI, since the generated catalog currently does not retain `highways` paths. [L3]
4. Keep parsing, manifest resolution, peak-source reading, matching, CSV encoding, file replacement, and stdout/stderr behind injectable Dart boundaries. Use a temporary sibling file followed by rename for atomic replacement, and clean up that sibling if writing or renaming fails. The shell launcher must record the exact Dart entry point used to build the shared macOS `peak_bagger` executable and rebuild when that recorded target differs from its target; it must establish the repository root before executing either an injected or built executable. [L12] [L13] [L16]
5. Parse the source CSV into `Peak` values without opening ObjectBox. Preserve its validated field values when creating the 22-column output rows, except write `region` as its normalized matching source-region value; write the generated membership `points` value separately as `1`. [L8] [L16] [L17]

## Testing Strategy

1. Use test-first Flutter unit coverage under `test/tool/` for CLI argument parsing, `--help`, canonical region-key normalization, default values, invalid arguments, supported-region listing, exit-code/stdout/stderr behavior, and shell-launcher argument forwarding from outside the repository root through an injected executable. Verify that the launcher establishes the repository-root working directory and rebuilds when a current source timestamp is paired with a recorded different Dart entry point. Verify the focused suite with `flutter test test/tool/` and the completed change with `flutter test`. [L13] [L15] [L17]
2. Add focused service tests with small fake manifest, Overpass, peak-source CSV, directory, and file-system inputs. Cover the required 25-column source schema; the required, optional, and MGRS-fallback row-validation cases; malformed source errors; ignored malformed top-level nodes; `way.nodes` resolution without bridging a broken reference; skipping individually malformed ways; failure for a file with no usable eligible segments; full `highway` eligibility including `area=yes` and `place=square` exclusions; 50 m inclusive segment boundaries; peaks outside the threshold; duplicate matches; source-region casing normalization with normalized source-region output; direct highway declarations; ancestor highway fallback; non-composite aliases; composite-region candidate unions using effective highway paths; multi-file sources; and header-only output. Do not load real large highway assets or require an API key/network connection. [L1] [L2] [L3] [L11] [L14] [L16] [L17]
3. Compare generated CSV fixtures against the app-owned export contract for all 22 headers, MGRS fallback, formatted values, `points: 1`, and name-then-`osmId` order. [L8] [L9]
4. Exercise missing parent directories, malformed peak sources, missing/unreadable or malformed highway inputs, and atomic replacement failures through faked file-system seams. Assert no partial target output, no retained temporary sibling, and actionable stderr. [L4] [L6] [L12] [L16]
5. Cover the default peak-source and output paths plus the injected CSV-reader boundary. Automated coverage is Flutter unit/service coverage only; no widget or robot journey is needed because this is a shell-run maintainer tool. [L16]

## Out of Scope

1. Persisting a generated `PeakList`, reading ObjectBox, or updating the peak source CSV. [L7] [L16]
2. Altering route-graph import, `RouteGraphWayIndex`, app UI, peak-correlation settings, or the existing app export flow.
3. Road-only filtering, highway elevation matching, network downloads, and automatic creation of highway source files or output directories. [L2] [L4] [L6] [L14]
4. Making a canonical manifest region selectable when neither it nor any of its manifest-priority ancestors declares one or more `highways` paths. [L17]
