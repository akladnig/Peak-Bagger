## Problem

The map screen `Search popup` can search tracks by name but cannot locate completed walks by their calendar day or show the peaks bagged on those walks. Users must remember track names and cannot use a date or inclusive date range to revisit historical activity. The normal input also treats date-like text as a failed name query instead of a date search.

## Proposed Outcome

The desktop map `Search popup` supports one transient Track date range selected from a custom picker next to the text field or entered directly as a complete date/date-range expression. The range is evaluated against canonical `GpxTrack.trackDate` calendar days. It returns matching tracks and, through `PeaksBagged`, each distinct peak bagged on those tracks while preserving existing result selection behavior. [L1] [L2] [L3] [L4] [L5]

## User Stories

1. As a map user, I want to select a Track date or date range beside the Search popup input, so I can find completed walks from a known day or period.
2. As a map user, I want a date-only search to show both my matching tracks and the peaks I bagged on them, so I can revisit an outing without knowing its name.
3. As a map user, I want to type familiar day-first dates and date ranges into the normal search input, so I can search historical activity quickly from the keyboard.
4. As a map user, I want invalid date-like input clearly identified, so it is not mistaken for an unsuccessful name search.

## Requirements

1. Scope this feature to the desktop map `Search popup` (`MapSearchPopup`). Preserve the existing popup entry points, result selection, close behavior, and text-only name search behavior except where an active date range changes result eligibility. [L2] [L9]
2. Add a separate custom Track date-range picker immediately to the right of the normal search text input. The picker opens and closes without closing the Search popup. No narrow-screen layout is required. [L2] [L9]
3. The picker trigger displays `Any date` when no range is active. After Apply, it displays a single-day range as `d MMM yyyy` and an inclusive range as `d MMM yyyy - d MMM yyyy`. [L7]
4. The picker supports a custom start and end date. Selecting only a start date means that one calendar day. Selecting or typing an end date while the start date is empty immediately copies that date into the start draft, creating a one-day range. Selecting both endpoints matches every Track date from the start through the end, inclusive. [L1] [L7]
5. The picker provides Apply, Cancel, Clear, and a top-right Close button. It opens with drafts copied from the active range, or empty drafts when none is active. Start and end each provide a synchronized editable field and custom calendar-grid control; each field accepts the supported single-date formats in requirement 11 and rejects range expressions. Each calendar opens to its endpoint draft month, otherwise its corresponding active-range endpoint month, otherwise the month containing `DateTime.now()`. It provides previous/next month controls and month/year navigation without changing drafts, supports Dart `DateTime` years 1 through 9999, and changes only its corresponding endpoint draft except that an end-date entry with no start draft copies its date into the start draft. Selecting or typing otherwise changes drafts only. Apply commits valid drafts, refreshes results, and closes the picker. Cancel, Escape, an outside click, and the Close button discard drafts, preserve any existing active range, and close the picker. While open, the picker consumes Escape before the enclosing Search popup can dismiss; clicks within the picker trigger or picker surface are not outside clicks, and all other Search popup clicks are. These picker close paths never invoke the Search popup close callback. Clear immediately removes the committed shared range, empties the drafts, restores normal text-only search, and keeps the picker open. Every picker close path restores focus to the date trigger. An end date earlier than its start date disables Apply until the draft range is valid. [L7]
6. A date range is a valid query even when the normal text field is empty. With no active date range, preserve the current three-character minimum for text-only search. With an active date range, an optional non-empty name query of any length narrows the returned tracks by track name and peaks by peak name. An active date range counts as an executed search for result presentation and pagination: empty range-qualified results use the existing no-results presentation, and range-qualified results can load subsequent pages with an empty or under-threshold optional name query. [L3] [L6] [L8]
7. Evaluate track eligibility only from each `GpxTrack.trackDate` device-local calendar day. Treat the persisted Track date's year, month, and day components as canonical and compare them directly with the picker/parser endpoint date components. Do not convert Track dates to Australian Eastern time or any other timezone. Ignore time-of-day. Tracks with no Track date cannot match a date range. Do not substitute GPX start or end timestamps. [L1] [L5]
8. For an active range, use `PeaksBagged` to retrieve distinct `Peak.osmId` values associated with Track-date-matching tracks. `PeaksBagged.peakId` stores that `Peak.osmId` reference, including valid negative synthetic IDs; it is not the ObjectBox `Peak.id`. Include a matching peak once even when multiple matching tracks bagged it. Do not filter directly on `PeaksBagged.date`, which may represent a different calendar day. [L4] [L5]
9. While a date range is active, apply entity filters as follows:
   - **All** returns Track-date-matching tracks and distinct matching bagged peaks.
   - **Peaks** returns distinct matching bagged peaks only.
   - **Tracks/Routes** returns Track-date-matching tracks only; routes are excluded.
   - **Maps** returns no results.
   Existing region, sort, group, pagination, and result-selection behavior continue to apply to eligible results. [L6]
10. Extend the normal text input to recognize a complete typed date or date range as the same active range selected by the picker. A valid typed expression supplies the active range with an empty effective name query, while retaining its raw text for display. Do not support mixed name-and-date expressions in one text value, such as `Bonnet 28 Jul 62`; a picker-selected range plus ordinary name input is the supported combined search path. [L10] [L13]
11. Parse typed dates in day-first Australian order. Support `d/M/yy`, `d/M/yyyy`, `d MMM yy`, and `d MMM yyyy`. Month abbreviations are ASCII `Jan` through `Dec`, case-insensitive; the month form accepts one or more spaces between date parts. Map two-digit years `00` through `49` to `2000` through `2049`, and `50` through `99` to `1950` through `1999`. [L11]
12. Treat `-` and `..` as inclusive typed date-range separators, with optional surrounding whitespace. For example, `28/7/62`, `28/07/1962`, and `28 Jul 62` each represent 28 July 1962; either supported separator can join two supported dates into a range. [L11]
13. Treat input as date-like when its trimmed value begins with a digit and contains a slash or a supported range separator, or when it begins with a one- or two-digit numeric day followed by an alphabetic token. A date-like value that cannot form a real supported calendar date or range, including a partial date expression, shows the exact inline message `Enter a valid date or date range` and returns no results. Non-date-like input remains a normal name search; for example, `123 Peak` remains a name query. Invalid date-like input must not silently become a failed name search. [L12]
14. Keep raw text, parsed input state, and the effective name query distinct. A valid typed date expression updates the picker trigger to the same active range and has an empty effective name query. Applying a range in the picker clears any typed date expression so the text field can accept an optional name query. Clearing a typed date expression removes only its typed-source active range. Clear in the picker removes the shared active range immediately as specified in requirement 5. Replacing a typed date/date-range expression with any non-valid expression immediately removes its typed-source active range; if its replacement is date-like, show the validation state with no results and no search candidates. An ordinary non-date-like replacement becomes the effective name query. A picker-originated active range remains active while the text field is empty or contains an ordinary optional name query. [L13]
15. When an active date range produces no eligible results, use the existing no-results presentation rather than retaining stale results. No loading, offline, retry, external-service, logging, or secret-handling behavior is introduced because this is a synchronous local-data search. [L3] [L12]

## Technical Decisions

1. Represent the active range as one transient Search popup criterion alongside query, entity filter, region filter, sort, group, pagination state, and request serial. The result-list presentation also receives the active-range/executed-search state so it can show no-results and allow load-more independently of text length. Updating, clearing, or replacing the range must reset the loaded page and invalidate outstanding load-more work just like another search criterion change. [L7] [L13]
2. Extend the shared `MapSearchService` search-page contract and the MapNotifier forwarding path with the active date-range criterion. Apply it before creating result entries so pagination, sorting, grouping, and entity filtering operate only on eligible tracks and peaks. [L3] [L6]
3. Supply the existing `PeaksBaggedRepository` to the shared map search seam. Filter tracks directly by the persisted device-local calendar-day components of `GpxTrack.trackDate`, then resolve distinct associated `Peak.osmId` values through `PeaksBagged`; do not make `PeaksBagged.date` a second date source of truth. Do not change the existing `PeaksBagged` date-derivation behavior. [L4] [L5]
4. Keep ordinary peak search repository behavior for text-only search. Range-qualified peaks are a separate result candidate set limited by the eligible `PeaksBagged` IDs, then subject to the existing peak result enrichment and region handling. [L4] [L6]
5. Implement deterministic date-expression parsing as app-owned Dart logic with explicit supported formats, range delimiters, date-like classification, calendar validation, whitespace and month-case rules, and two-digit-year mapping. Reuse its single-date grammar for picker start/end fields, rejecting range expressions there. Do not rely on locale-dependent or sliding-window parsing. [L10] [L11] [L12]
6. Keep picker edits local until Apply, except that Clear immediately clears the committed shared range and drafts while leaving the picker open. The Search popup owns temporary picker and typed-input UI state and must clean up any controllers or transient popup state when dismissed. Picker start/end fields and calendar controls must be keyboard-accessible with semantic labels. Cancel, Escape, outside-click, and Close-button dismissal preserve the committed range, close the picker, and restore focus to the trigger. The map-level search-field autofocus applies only when opening the Search popup and must not override picker-trigger focus restoration after a range-state update. Provide the picker with an injectable `DateTime Function()` clock that defaults to `DateTime.now()` for its fallback month. Do not persist an active range, search text, or search results across app sessions. [L7] [L13]
7. Preserve existing desktop `Key`-based Search popup test selectors and add stable selectors for the date trigger, picker start/end controls, calendar navigation controls, Apply, Cancel, Clear, and inline validation state. [L2] [L7] [L12]

## Testing Strategy

1. Use behavior-first TDD for date-expression parsing and date-qualified search-page logic. [L1] [L5] [L11] [L12]
2. Extend `MapSearchService` unit tests using `InMemoryGpxTrackStorage`, `InMemoryPeakStorage`, `PeaksBaggedRepository.test`, and `InMemoryPeaksBaggedStorage` to verify:
    - a single Track date and an inclusive range include only matching tracks by their persisted device-local calendar-day components, without timezone conversion;
   - undated tracks are excluded;
   - `PeaksBagged` returns each associated peak once;
    - a difference between `GpxTrack.trackDate` and `PeaksBagged.date` does not change eligibility;
    - `PeaksBagged.peakId` resolves by `Peak.osmId`, not ObjectBox `Peak.id`, including a negative synthetic ID;
   - entity-filter, optional name, region, sorting, grouping, and pagination contracts hold with an active range; and
   - routes and maps do not appear in range-qualified results. [L3] [L4] [L5] [L6] [L8]
3. Add parser unit coverage for every supported date format, both separators, range inclusivity, deterministic two-digit-year boundaries, whitespace and month-case rules, unsupported mixed expressions, partial and invalid date-like input, and non-date-like numeric name input. Cover the same single-date grammar and range rejection for picker start/end fields. [L10] [L11] [L12]
4. Extend Search popup widget coverage for the right-side picker trigger, exact `Any date`, `d MMM yyyy`, and `d MMM yyyy - d MMM yyyy` labels, synchronized calendar and editable start/end controls, endpoint-specific calendar updates, calendar navigation, the fallback month using an injected fixed clock, and historical-date selection. Cover start-only, end-first auto-copy, and two-endpoint Apply behavior, reversed-range Apply disabling, Escape consumption before outer Search popup dismissal, outside-click/Close-button Cancel preservation and focus restoration, and immediate Clear reset while the picker stays open. Verify date-only results, typed dates use an empty effective name query, the minimum-length bypass while a range is active, exact validation copy, no stale results for invalid or unmatched ranges, the no-results presentation for an empty date-only range, and load-more for date-only and one-character optional-name range queries. [L2] [L7] [L8] [L12] [L13]
5. Extend the existing desktop AppBar search robot journey with deterministic tracks, peaks, and `PeaksBagged` rows. Cover picker-driven date-only selection of a track and a bagged peak, plus typed date input and date-range input. Use the new stable selectors and repository fakes; do not use ObjectBox, network services, API keys, or external secrets. [L2] [L3] [L4] [L7] [L10]

## Out of Scope

1. Narrow-screen, mobile, responsive, or text-scale-specific date-picker layouts. The app and this feature are desktop-only. [L9]
2. Date filtering for routes, maps, natural features, roads, or unrelated search surfaces outside the map Search popup. [L6]
3. Natural-language mixed name-and-date queries, date presets, relative-date shortcuts, and user-configurable date parsing. [L10] [L11]
4. Persisting the active date range or name query between popup sessions or app launches. [L7] [L13]
