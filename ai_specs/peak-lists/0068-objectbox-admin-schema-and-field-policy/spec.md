## Problem

ObjectBox Admin discovers entities from the generated model, but schema descriptors currently render property types as strings such as `type6` and hardcode `nullable: false`. The Schema view uses basic list tiles with limited attributes. It cannot accurately communicate Dart types, nullability, ID assignment, relationships or Admin edit eligibility. Some existing edit forms also create disabled `TextFormField`s for read-only values. Long-value handling is inconsistent, and `SelectableText(maxLines: 5)` alone does not establish independently scrollable access to complete values. [L1] [L3] [L5] [L6] [L7] [L10]

The template demonstrates readable types and attributes, but its schema descriptors are handwritten display strings for its own sample entities. Copying those strings would not describe Peak Bagger's field policies accurately. [L2] [L3]

## Proposed Outcome

Provide a read-only **Field / Type / Attributes** schema table for every persisted entity, backed by actual ObjectBox model discovery and structured Peak Bagger metadata. Use one field-edit policy for displayed Admin editability and existing hand-built form eligibility. Render read-only form values as labelled selectable content without text-field widgets, and give all long detail/form values independently scrollable viewports capped at five rendered lines. [L1] [L3] [L4] [L6] [L7] [L10]

The approved refinement also includes consistent Cancel / Save behaviour for the five affected editors, bounded central field/grid styling alignment as a prerequisite to the dependent UI work, and Schema availability independent of Data reads. Subsequent clarifications explicitly cover retained-shell navigation during Save, schema-discovery Retry/recovery and permitted framework-managed read-only selection internals. These decisions are recorded under Refinement decisions below and in ledger records L11–L13; the earlier interview answers remain unchanged.

Keep the database schema, identities, existing editable capabilities, validation, domain actions and stored content unchanged. Template implementation is separate. The subsequent L14–L16 decisions resolve this feature's window/layout blockers: support 1280 × 960 logical points and larger with no fixed maximum, retaining one wide layout with wrapping/scrolling and no additional breakpoints. [L1] [L2] [L6] [L9] [L14] [L15] [L16]

## User Stories

1. As an administrator, I can inspect readable types and accurate attributes for every persisted entity, even if it has no records. [L1] [L3] [L4]
2. As an administrator, I can distinguish nullability, required input, ID assignment, uniqueness, relationships and direct Admin editability without confusing storage facts with form rules. [L3] [L5] [L6] [L8]
3. As an administrator editing a supported record, I can see and copy read-only values without being presented with disabled text fields, while keeping the existing editable fields and validation. [L6] [L7]
4. As an administrator inspecting or editing a long value, I can scroll and select content beyond its fifth rendered line without losing content or expanding every short value to five lines. [L10]
5. As a maintainer, I can detect metadata drift against the generated model without maintaining a second independent entity list or migrating the database. [L1] [L3] [L4]

### R3. Read-only schema table and attribute meanings

1. In the existing `Schema` mode, replace the field list with a read-only table whose visible columns, in order, are **Field**, **Type**, **Attributes**. Preserve the `Entity` selector and `Schema / Data` destination/mode labels. The schema table itself has no record-editing or schema-mutation actions. [L1] [L4]
2. Use readable Dart-facing types, including `int`, `double`, `bool`, `String`, nullable `?`, `DateTime` and actual collection/relationship types where applicable. Do not confuse an ObjectBox storage code with a Dart declaration: dates stored as integer values must not appear simply as `int`. Do not infer a type from a sampled record or missing value. [L1] [L3] [L5] [L8]
3. Keep attributes structured; construct the visible attribute list from their values. Use these exact terms where applicable: [L1] [L3] [L5] [L6]

   | Attribute | Meaning |
   | --- | --- |
   | `PK` | The model's primary-key property. |
   | `Generated` | An explicitly identified generated value; normal non-assignable ObjectBox IDs use `PK · Generated`. Do not classify every read-only field as generated. |
   | `Assignable` | An ObjectBox ID declared assignable, for example `Peak.id`; use `PK · Assignable`, not an unconditional claim that it is generated-only. |
   | `Name` | The field actually designated as the existing primary display-name/title field, not an invented name field on a maintenance entity. |
   | `Nullable` | The Dart field value can be null. |
   | `Non-nullable` | The Dart field value cannot be null; empty strings and numeric defaults are separate matters. |
   | `Required` | Existing Admin validation unconditionally requires that individual input. This does not change validation. |
   | `Unique` | An actual model uniqueness constraint. |
   | `Read-only` | No direct editable Admin field is permitted by the field-edit policy. This is not a database-wide write restriction. |

4. Preserve the distinction established by these examples: `Peak.name` is `String` with `Name · Non-nullable · Required`; `Peak.altName` is `String` with `Non-nullable`; `Peak.peakbaggerPid` is `int?` with `Nullable`. `Contact.firstName` is `String` with `Name · Non-nullable`, not individually Required, because existing validation accepts any one of first name, surname or nickname. Other applicable attributes may be composed with these examples. [L5]
5. Derive Required from existing form/validation policy, not Dart constructor `required`, non-nullability, current record content or a grouped/conditional validation rule. This feature is not a new comprehensive validation-rule language. Preserve the current coordinate-input alternatives and conversions. [L3] [L5]
6. Preserve date-only versus timestamp semantics from the profile. In particular, `GpxTrack.trackDate` is the walk's calendar day despite its `dateUtc` storage annotation; do not label it as an instant or shift its day. Additional type/storage information must not override the existing display-formatting rules. [L3]

### R4. Relationships and stored/Dart names

1. Keep the actual generated-model property name in **Field**. When a Dart relationship alias differs, show its actual relationship type in **Type**, and identify its alias and target in **Attributes**. Do not display duplicate rows for the relationship and its backing property. [L8]
2. Required example: `PeakListItemEntity` includes `peakListId | ToOne<PeakList> | Dart field: peakList · → PeakList · Read-only`, supplemented only by independently accurate applicable attributes. A `ToMany` relationship such as `GpxTrack.peaks` identifies its actual type and target. [L8]
3. An ordinary stored integer such as `PeaksBagged.peakId` remains `int`. Do not manufacture ObjectBox relations based on an `Id` suffix, or change storage/relationship behaviour to match the presentation. [L1] [L8]
4. For relationship metadata, distinguish nullability of the Dart wrapper from whether its target can be absent. Do not treat a non-nullable `ToOne` wrapper as proof of a required target or add a target-validation rule absent from existing behaviour. [L3] [L5] [L8]

### R5. Authoritative Admin field-edit policy

1. Use one structured field-edit policy for the Schema `Read-only` attribute and eligibility to create a direct editable Admin control. Eligibility must be explicitly enabled; missing metadata never enables an input. ID assignment, generated status, nullability and editability remain separate facts. [L3] [L6]
2. All primary keys are non-editable in Admin, including assignable IDs. Explicitly system-managed generated values likewise receive no direct editing input. A generated-looking or calculated-looking name is not sufficient reason to revoke an existing supported editor. [L6]
3. Preserve the following source-observed direct editing capabilities, through the same hand-built forms and existing validators. All other persisted fields have no direct Admin field editor; this does not add an editor for an unsupported entity. [L5] [L6]

   | Entity | Existing direct editable fields to retain |
   | --- | --- |
   | `Peak` | `name`, `altName`, `osmId`, `peakbaggerPid`, `elevation`, `prominence`, `country`, `county`, `range`, `rating`, `durationLabel`, `difficulty`, `viaFerrata`, `notes`, `latitude`, `longitude`, `region`, `mgrs100kId`, `easting`, `northing`, `verified` |
   | `NaturalFeature` | `name`, `altName`, `tag`, `country`, `county`, `region`, `latitude`, `longitude`, `mgrs100kId`, `easting`, `northing`, `sourceOfTruth` through its existing `OSM / Manual` selector |
   | `Contact` | `firstName`, `surname`, `nickname` |

   | `PeakList` | `colour` |

4. Keep field policy distinct from supported domain actions and derivations. For example, `Peak.sourceOfTruth` has no direct text editor but retains its existing **Mark as HWC** action; coordinate calculation and duration parsing can still update their legitimate derived fields. Natural Feature identity/source-key maintenance remains owned by its existing operation. Do not turn the presentation policy into a blanket denial of legitimate service writes. [L6]
5. Preserve unchanged fields when existing save paths rebuild records. Do not write back read-only presentation strings, missing-value placeholders or `Not yet assigned`, and do not discard hidden persisted values. This feature does not authorise new validation, new mutable fields, new create flows or new record writes at render time. [L1] [L5] [L6] [L7]

### R6. Read-only form values

1. Replace read-only text-field widgets in affected existing Admin forms with labelled selectable content. Create neither `TextField` nor `TextFormField` for a read-only value, even with `enabled: false` or `readOnly: true`. Existing read-only values and labels remain visible rather than disappearing. [L6] [L7]
2. Retain copy/select support and accessible label/value association. The read-only presentation must not advertise a text-editing action or require an app-owned `TextEditingController` solely for display. Framework-managed read-only selection internals, including `EditableText(readOnly: true)` inside `SelectableText`, are permitted; they do not relax R6.1's ban on `TextField`/`TextFormField` or permit text mutation or text-mutation accessibility actions. Preserve existing appropriate scalar/boolean semantics and formatting. [L7] [L13]
3. Show exact text **Not yet assigned** for a new record's generated value that is genuinely not assigned yet. Do not replace valid persisted zero/empty values or other fields' existing missing-value presentation with that placeholder. Replacing a disabled widget must not change ID assignment or save behaviour. [L1] [L7]

### R7. Universal five-line value viewports

1. Apply a maximum viewport of **five rendered text lines** to every long value in ObjectBox Admin record details, read-only edit-form displays and existing editable multiline text fields. This is not restricted to Route/GPX field-name lists. Values in schema metadata columns wrap normally; Data-grid preview-cell policy is not being redesigned. [L10]
2. Each long value scrolls independently, retaining its complete stored/displayed text. Access beyond line five must not depend solely on scrolling the outer panel. Read-only text remains selectable/copyable, including content outside the initial viewport. Do not use ellipsis, substring previews or destructive transformations as a substitute. [L10]
3. Calculate the cap using active text style, line metrics, available wrapping width and actual text scale. Recalculate for changed constraints/theme/text scale as needed; do not impose an unscaled fixed pixel height. `SelectableText(maxLines: 5)` alone is not sufficient proof of this behaviour. [L10]
4. Short values use only their required height. Empty editable multiline controls retain their normal one-line input minimum rather than a forced three/five-line body. Existing single-line inputs remain single-line. The five-line cap concerns rendered value/input content, not field labels, inline validation or the whole enclosing form. [L10]
5. Preserve full editable draft text, selection and existing save/validation behaviour while scrolling or resizing. Do not save, cancel or replace a draft as a side effect of viewport measurement or widget rebuild. [L6] [L10]

## Technical Decisions

1. Preserve `ObjectBoxAdminRepository.getEntities()` and the injected `getObjectBoxModel()` seam as the source of persisted coverage. Extend the current descriptor boundary or a small adjacent metadata module; do not hardcode a second replacement entity list in widgets. Generated model metadata supplies facts such as property identity, PK/assignable flags, uniqueness and actual ObjectBox relationships where available. Explicit app descriptors supply facts it cannot reliably express, notably Dart nullability, display-name policy and direct editor requirements. [L3] [L4] [L5] [L8]
2. Store editability, required input and other field facts as structured values, not by parsing the rendered Attributes string or deducing flags from record content. Exact class/enum names are implementation choices; the same authoritative policy must be consumed by schema rendering and existing hand-built editor composition. Preserve the current explicit source-of-truth/action boundaries. [L3] [L6]
3. For all current model members, provide complete reviewed metadata. Supporting resilience default: if a future model member lacks app metadata, keep its actual name/storage type available, disclose unavailable app metadata, and fail closed for new editing eligibility rather than guessing nullability/Required. Unknown storage codes retain an intelligible numeric fallback. Coverage tests must fail for missing/stale mappings, even though a runtime fallback keeps browsing usable. [L3] [L4] [L6]
4. Keep Riverpod repository/provider injection and existing editor/service/data-access boundaries. Widgets render state and dispatch existing intents; they do not acquire new `Store`/`Box` operations. Persisted records remain ObjectBox-owned, with drafts separate from committed values. No new preference, network service, shared package, global cache or automatic form generator is required. [L1] [L2] [L3] [L6]
5. Reuse a small shared read-only value presentation/viewport component across generic and entity-specific detail/form paths, using actual local equivalents. Framework-managed read-only selection internals are permitted under R6.2. Give any app-owned scroll/focus/selection controllers explicit widget/provider lifecycle owners; dispose them and avoid scroll-position state keyed only by list index when identity can change. Do not close the app-owned store from a field widget. [L7] [L10] [L13]
6. Do not change entity annotations, model UIDs/history, `objectbox-model.json` or `objectbox.g.dart` to implement presentation metadata. No schema regeneration is expected. If later work genuinely changes entity source, it needs separately scoped supported generation/migration and existing-data verification; never hand-edit generated bindings. [L1] [L3]
7. Implement shared styling in the existing `lib/theme.dart` owners, with effective seed/scheme inputs available where required. The prerequisite owns the central field decoration/tokens, shared mode-layer definitions needed for field hover, applicable `DataGridTheme` metrics and amended state roles, plus removal of conflicting affected Admin overrides. Reuse these definitions rather than creating a screen palette or changing the global scheme to fake a local divider role. Inspect existing consumers and add regression coverage for the impact of central changes; preserve their data, validation, navigation and action semantics. This is not an app-wide component/layout compliance sweep. Integrate and verify dependent UI against R1's now-approved supported range and single-wide-layout contract; the shared-theme prerequisite remains an implementation dependency, not an unresolved layout decision.
