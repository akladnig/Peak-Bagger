title: Martin-Backed Tasmania Local Topo Preview Defaults

## Problem

The Tasmania `Local Topo` stack currently defaults to static prerendered delivery and relies on the legacy TileServer-backed OSM preview path, which blocks native preview `z17` and `z18` OSM detail, mixes preview-vs-static maintainer intent, and makes direct comparison between a future Martin-backed OSM preview source and the legacy source cumbersome. The stack also needs a durable boundary between `Preview style`, `Prerender zoom range`, and `Contour cartography` so future rebuild decisions stay explicit. [L1] [L2] [L3] [L4] [L5]

## Proposed Outcome

Make Tasmania preview mode the default maintainer stack behavior, keep the app-facing raster route and capability contract unchanged, and let the existing Flutter `Local Topo` basemap consume native Tasmania `z17` and `z18` detail through a Martin-backed preview OSM source served from Docker Compose-managed `PostGIS` through `Martin`. Preserve startup-scoped maintainer selection through `LOCAL_TOPO_STYLE` for preview style choice and `LOCAL_TOPO_TILESERVER` for OSM-backed preview backend choice, keep the existing legacy OSM-plus-contours preview style intact, and add a Martin-specific preview style copy that becomes the default preview style after the minimal Martin-schema compatibility edits required for the first slice. Build preview OSM data from the exact same selected Tasmania extract contract already used by refresh commands, not during startup, and use a smaller repo-owned `osm2pgsql` `flex` schema limited to the required preview layers. [L2] [L4] [L5] [L6] [L7] [L8] [L9] [L10] [L11] [L12] [L13] [L14]

## User Stories

1. As a maintainer, I can run `npm run stack:up` and get the Martin-backed Tasmania preview stack by default, using the same raster preview route the app already expects. [L5] [L12] [L13]
2. As a maintainer comparing cartography and performance, I can switch between the Martin-backed and legacy TileServer-backed OSM preview sources without changing the app-facing route shape or rewriting the comparison path each time. [L11] [L12] [L13]
3. As a maintainer rebuilding Tasmania preview data, I can refresh the Martin-backed OSM database from the same selected Tasmania extract used elsewhere in the stack, while keeping prerender behavior unchanged and preserving the last successful preview database if a new import fails. [L2] [L6] [L9] [L10]
4. As a Flutter app user, I can keep using the existing `Local Topo` basemap entry and receive native Tasmania `z17` and `z18` tiles without any new basemap drawer choice, while a later slice may still add `Local Topo Legacy` as a separate comparison option. [L2] [L5] [L14]

## Requirements

1. Treat `Preview style`, `Prerender zoom range`, and `Contour cartography` as separate canonical concepts throughout the Tasmania local topo workflow and documentation. [L1]
2. Preview `z17` and `z18` are preview-only changes to `Local Topo`. This slice must not change the prerender zoom range or static prerender behavior, but it must make native Tasmania `Local Topo` `z17` and `z18` app-consumable through the unchanged raster route and `GET /capabilities` contract. [L2] [L5] [L14]
3. The preview OSM upgrade target is regenerated higher-zoom preview data, not overzoom-only rendering. [L3]
4. `npm run stack:up` must start preview mode by default. Keep `npm run stack:up:static` as the explicit static startup command for the previous behavior, and keep the explicit preview alias `npm run stack:up:preview` for clarity. Any touched repo-standard maintainer startup helper, including `./run_local_maps.sh`, must align with this preview-default behavior rather than preserving a separate implicit static-default path. [L5]
5. `LOCAL_TOPO_STYLE` is the maintainer-facing preview-style selector in this slice. Its supported values are exactly `tasmania-openstreetmap-contours-martin`, `tasmania-openstreetmap-contours`, `tasmania-maptiler-topo`, and `tasmania-maptiler-outdoor`. The default preview style must be exactly `tasmania-openstreetmap-contours-martin`. The legacy comparison style id `tasmania-openstreetmap-contours` must remain available. Static startup mode ignores `LOCAL_TOPO_STYLE` because static prerender delivery does not select an on-demand preview style. [L5] [L12]
6. The default startup path must fail fast when preview prerequisites are missing or unhealthy. It must not silently fall back to static prerendered tiles or deterministic smoke fixtures. Any touched maintainer startup helper that launches the stack for Flutter development must preserve that explicit failure behavior instead of hiding it behind helper-specific fallback heuristics. [L5]
7. Keep the app-facing HTTP contract unchanged in this slice. The gateway must continue serving raster PNGs from `/tasmania/local-topo/{z}/{x}/{y}.png`, and `GET /capabilities` must remain unchanged for the Flutter app. Raw vector tile endpoints remain internal to the preview stack. [L5]
8. The app-owned `Local Topo` native zoom cap for Tasmania must change from exactly `16` to exactly `18` so the existing `Local Topo` basemap can request native `z17` and `z18` tiles from the unchanged local tile server route. `GET /capabilities` remains unchanged in this slice and does not become the source of truth for native zoom limits. [L2] [L5]
9. The preview OSM database must be derived from the exact existing Tasmania OSM extract-selection contract already used by the rebuild workflow. Normal rebuild selection continues using `LOCAL_TOPO_OSM_EXTRACT_PATH` or its existing default managed-cache location, and `LOCAL_TOPO_OSM_EXTRACT_OVERRIDE` remains the explicit local override seam. Martin preview import must consume the same selected extract resolved through those seams. `npm run stack:up`, `npm run stack:up:preview`, and `npm run stack:up:static` stay serve-only and must not download, select, copy, import, or rebuild OSM data on demand. [L6]
10. Docker Compose-managed `PostGIS` is the canonical preview OSM runtime for this workflow and the only required runtime path for this first Spec. [L6]
11. Build and refresh the preview OSM database during `npm run refresh:manual` and `npm run refresh:scheduled`. Treat it as maintainer-managed derived state rather than a checked-in artifact. `npm run refresh:scheduled` must preserve the current stale-managed-extract fallback behavior when refresh download fails and a previously usable managed extract already exists. This slice must not broaden that scheduled-only fallback into `npm run refresh:manual`. [L6]
12. The Martin-backed preview OSM schema may be smaller than full OpenMapTiles compatibility, but it should preserve current vector layer names where practical so the style rewrite stays minimal. [L7]
13. The first Martin-backed preview schema must include only these required OSM vector layers: `landcover`, `landuse`, `water`, `water_name`, `waterway`, `transportation`, `transportation_name`, `building`, `place`, `park`, and `boundary`. [L8]
14. The first Martin-backed preview schema must explicitly defer these OSM layers: `aerodrome_label`, `aeroway`, `housenumber`, `mountain_peak`, and `poi`. [L8]
15. Import the Martin-backed preview OSM data with repo-owned `osm2pgsql` `flex` configuration that loads only the required preview layers and attributes into a preview-specific PostGIS schema. This slice must not adopt the full OpenMapTiles import pipeline. [L9]
16. If contours and relief rebuild successfully but the preview OSM import fails, the refresh run must fail clearly, keep the last successful published Martin preview dataset active, and avoid publishing a partially replaced preview dataset. For this slice, Martin must serve normal preview traffic only from the fixed active PostGIS schema `local_topo_preview_active`. A refresh run must import into the staged PostGIS schema `local_topo_preview_stage` first and must promote that staged schema into `local_topo_preview_active` only after import and validation succeed. Validation must read `local_topo_preview_stage` directly before promotion. If tile-read validation is used, it must run through a staged validation seam rather than the normal active preview route. The minimum validation contract before promotion is: the staged schema contains the required first-slice layers, deferred layers are not required for success, the staged dataset is readable through the expected Martin configuration, deterministic schema-read validation passes, and an explicit Martin restart occurs as part of successful promotion so the publish boundary stays deterministic. [L10]
17. Add a startup-scoped OSM-backed preview backend selector through `LOCAL_TOPO_TILESERVER=martin|tileserver`, defaulting to `martin`. `LOCAL_TOPO_TILESERVER=tileserver npm run stack:up` must remain a supported comparison path. This selector applies only to the OSM-backed preview styles in this slice and does not retarget `tasmania-maptiler-topo` or `tasmania-maptiler-outdoor`. This slice replaces the previous maintainer environment variable names rather than supporting both in parallel: touched docs, tests, commands, and helpers must use `LOCAL_TOPO_STYLE` and `LOCAL_TOPO_TILESERVER` only. [L11] [L13]
18. Keep the legacy comparison style wiring as:
    - style id `tasmania-openstreetmap-contours`
    - file `styles/local-topo/openstreetmap.json` [L12]
19. Add Martin-specific comparison style wiring as:
    - style id `tasmania-openstreetmap-contours-martin`
    - file `styles/local-topo/openstreetmap-martin.json` [L12]
20. `styles/local-topo/openstreetmap-martin.json` must be created as a separate committed file derived from `styles/local-topo/openstreetmap.json`, but the Martin file may then make only the explicitly allowed first-slice compatibility edits needed to stay compatible with the first Martin-backed preview schema: source rewrites, source-layer rewrites, and removal or rewrite of references to deferred first-slice layers absent from the Martin-backed preview schema. In this first slice, those edits must preserve matching cartography wherever the agreed Martin schema supports it and must not expand the schema solely to preserve deferred legacy layers. [L8] [L12]
21. Before `tasmania-openstreetmap-contours-martin` becomes the default preview style, the Martin style file must remove or rewrite any references to deferred first-slice layers that are not present in the Martin-backed preview schema: `aerodrome_label`, `aeroway`, `housenumber`, `mountain_peak`, and `poi`. [L8] [L12]
22. The preview stack must support explicit maintainer A/B comparison between the legacy TileServer-backed OSM source and the Martin-backed OSM source while keeping the same raster preview route shape and style-driven rendering path. [L11]
23. Keep the existing preview style ids `tasmania-maptiler-topo` and `tasmania-maptiler-outdoor` registered and functional in this slice. Aside from any stack wiring needed to keep them working after the preview-default changes, this Spec does not change their cartography or selector semantics, and `LOCAL_TOPO_TILESERVER` does not retarget them. [L11] [L12]
24. This first Spec must leave the current Flutter basemap drawer choices and labels unchanged. Flutter app changes needed to let the existing `Local Topo` basemap consume native Tasmania `z17` and `z18` tiles are in scope, but exposing a separate `Local Topo Legacy` drawer choice remains out of scope. [L14]

## Technical Decisions

1. Keep the Martin migration scoped to the existing Flutter app-facing `Local Topo` contract rather than adding a new app-facing basemap, route, or drawer choice. This preserves the existing raster route, capability contract, and app-side selection flow while allowing app-side zoom behavior and the preview backend to change. [L5] [L14]
2. Use Docker Compose-managed `PostGIS` and `Martin` as repo-owned preview infrastructure so the canonical workflow stays self-contained beside the existing Tasmania stack. Host-installed `PostGIS` is not part of the required first-slice workflow. [L4] [L6]
3. Prefer a smaller repo-owned `osm2pgsql` `flex` import over full OpenMapTiles compatibility so the first Martin slice can target only the layers actually needed by the first Martin-backed preview style after its minimal schema-compatibility rewrites. [L7] [L8] [L9] [L12]
4. Keep the legacy OSM-plus-contours style and the Martin-specific style as separate committed style ids and files rather than mutating the legacy file in place. This keeps A/B comparison explicit and avoids hidden schema drift while `LOCAL_TOPO_STYLE` remains the single maintainer-facing preview-style selector. [L11] [L12]
5. Keep OSM-backed preview backend comparison startup-scoped through `LOCAL_TOPO_TILESERVER` while `LOCAL_TOPO_STYLE` remains the startup-scoped preview-style selector. This is the smallest compatible seam with the current preview stack, and `LOCAL_TOPO_TILESERVER` applies only to the OSM-backed comparison styles rather than the existing MapTiler-derived preview variants. [L11] [L12] [L13]
6. Preserve the exact existing Tasmania OSM extract-selection seams through `LOCAL_TOPO_OSM_EXTRACT_PATH` and `LOCAL_TOPO_OSM_EXTRACT_OVERRIDE`, and keep any out-of-tree staging copy behavior as an internal rebuild seam rather than a new maintainer-facing contract. [L6]
7. Preserve the last successful preview OSM database on import failure rather than replacing it with a partial or broken rebuild, while still failing the refresh run so maintainers do not mistake the state for a successful refresh. Use fixed-schema staged PostGIS promotion from `local_topo_preview_stage` into `local_topo_preview_active`, with an explicit Martin restart after successful promotion, so failed imports cannot replace the active published preview dataset and the publish boundary stays deterministic. [L10]
8. Keep the app-side `Local Topo` zoom change in the existing app-owned basemap metadata seam rather than introducing a new runtime negotiation contract through `GET /capabilities`. Preserve the current Tasmania stack testing posture by making script, config, gateway, and app-side zoom behavior deterministically testable without requiring live Docker Compose, `PostGIS`, or `Martin` services in the primary automated regression suite. Live stack startup may be used for smoke verification only. [L5] [L6] [L9] [L14]

## Testing Strategy

1. Add deterministic server-side coverage for the default stack startup contract proving that `npm run stack:up` enters preview mode by default, defaults `LOCAL_TOPO_STYLE` to `tasmania-openstreetmap-contours-martin`, defaults `LOCAL_TOPO_TILESERVER` to `martin`, and fails fast rather than silently falling back when preview prerequisites are missing. Extend touched maintainer startup helper or doc assertions where such coverage already exists so `./run_local_maps.sh` and related guidance do not preserve contradictory static-default behavior. [L5] [L12] [L13]
2. Add deterministic coverage for the OSM-backed preview backend selector proving that `LOCAL_TOPO_TILESERVER=martin|tileserver` selects the expected internal OSM-backed preview path while `LOCAL_TOPO_STYLE` remains the maintainer-facing preview-style selector and `/tasmania/local-topo/{z}/{x}/{y}.png` plus `GET /capabilities` stay unchanged. [L5] [L11] [L12] [L13]
3. Add deterministic configuration and style-structure tests proving the supported `LOCAL_TOPO_STYLE` values are registered, `tasmania-openstreetmap-contours-martin` maps to `styles/local-topo/openstreetmap-martin.json`, and any first-slice divergence from `styles/local-topo/openstreetmap.json` is limited to the explicitly allowed source rewrites, source-layer rewrites, and deferred-layer removals or rewrites required for Martin-schema compatibility. [L8] [L12]
4. Add deterministic import and schema coverage for the new `osm2pgsql` `flex` workflow by asserting generated command arguments, required-layer mapping, deferred-layer omission, schema-target selection to `local_topo_preview_stage`, promotion into `local_topo_preview_active`, required schema-read validation, any staged tile-read validation seam used in addition to schema-read validation, and the explicit Martin restart publish step through script-level test seams or fixtures rather than requiring live external services in the primary automated test path. [L7] [L8] [L9] [L10]
5. Add deterministic refresh-path coverage proving preview OSM rebuilds reuse the exact existing extract-selection workflow through `LOCAL_TOPO_OSM_EXTRACT_PATH` and `LOCAL_TOPO_OSM_EXTRACT_OVERRIDE`, preserve the scheduled stale-managed-extract fallback behavior, never import during `stack:up`, `stack:up:preview`, or `stack:up:static`, stage Martin preview imports into `local_topo_preview_stage` first, require the defined validation gate before promotion, and keep `local_topo_preview_active` in place if a new import, validation step, or promotion step fails. Treat any live Docker Compose, `PostGIS`, or `Martin` run as optional smoke verification rather than the required regression seam. [L6] [L9] [L10]
6. Add deterministic preview routing or gateway tests proving the Martin-backed and legacy OSM comparison paths both continue serving the unchanged raster route through the gateway, that `LOCAL_TOPO_TILESERVER` selects only those OSM-backed comparison paths, and that non-OSM preview styles keep their existing routing contract. [L5] [L11]
7. Keep deterministic configuration or routing coverage proving `tasmania-maptiler-topo` and `tasmania-maptiler-outdoor` remain registered and functional after the preview-default changes, and that `LOCAL_TOPO_TILESERVER` does not retarget them. [L12]
8. Add Flutter Dart coverage proving the existing `Local Topo` basemap can request native Tasmania `z17` and `z18` tiles through the unchanged capabilities contract without changing drawer labels or basemap selection flow. Cover the risky app-side zoom behavior regression with deterministic tests at the existing app-owned basemap metadata seam by asserting the native zoom cap changes from exactly `16` to exactly `18`. If UI journey coverage is touched, reuse the existing stable `Local Topo` basemap selectors. [L2] [L5] [L14]

## Out of Scope

1. Changing the current Flutter basemap drawer to expose both comparison paths in this slice. [L14]
2. Changing the prerender zoom range, static prerender output contract, or baking preview `z17` and `z18` into the static PNG stack. [L2]
3. Preserving full OpenMapTiles schema compatibility for the first Martin-backed preview path. [L7]
4. Importing OSM data during `npm run stack:up` or making preview startup responsible for long-running data preparation. [L6]
5. Adding or documenting host-installed `PostGIS` as a required or equivalently supported first-slice runtime workflow. [L6]
6. Exposing backend implementation names such as `Martin` or `TileServer GL` as app-facing basemap labels in this slice. [L14]

## Follow-Ups

1. Add an app-side basemap drawer enhancement that lets users compare `Local Topo` and `Local Topo Legacy` directly, using those labels as the canonical future picker terms. [L14]
2. Expand the Martin-backed preview schema if later cartography review shows that deferred layers such as `poi` or `mountain_peak` are necessary for acceptable comparison quality. [L8]
3. Revisit host-installed `PostGIS` override documentation after the Docker Compose-managed canonical path is stable. [L6]
