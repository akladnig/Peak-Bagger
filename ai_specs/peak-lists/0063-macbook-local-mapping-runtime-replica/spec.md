## Problem

After the Services volume moved to the Mac mini, Peak Bagger on the MacBook became substantially slower. The corrected post-restart report is approximately 40+ seconds for initialization, an almost instantaneous start route point, and 20–30 seconds for subsequent route points, with the app becoming unresponsive and showing the macOS spinning wheel. These are user observations rather than instrumented measurements. [L1]

The MacBook currently mounts `/Volumes/Services` over SMB from `mac-mini.local`; the mini accesses the same canonical Mapping data store on its attached disk. Tasmania route elevation uses `DEM/Elvis/elvis_runtime_10m.tif`. Its GDAL adapter makes synchronous native raster reads on the UI isolate, and the draft samples both geometry-point elevations and a densified route summary after committed geometry changes. Network-backed sampling is a plausible contributor, but startup and point-placement bottlenecks have not been profiled. [L2]

Current startup requires the manifest pair, existence/readability checks for every region-manifest dataset reference, and required polygon geometry before opening the normal ObjectBox-backed app. Existing ObjectBox data does not bypass this preflight. The prior migration explicitly retained SMB runtime access and excluded Mapping data from the three project Mutagen sessions; a local runtime replica is a deliberate follow-up contract change. [L2, L3]

## Proposed Outcome

Restore fast, responsive MacBook startup and route creation using a complete local Mapping runtime replica. Keep `/Volumes/Services/Mapping` on the mini as the canonical Mapping data store. Automatically synchronize the app-required dataset mini → MacBook through a dedicated one-way Mutagen session, validate staged updates, and activate them only at the next app launch. A ready MacBook app reads local Mapping inputs without waiting for SMB, the mini, or synchronization. [L2, L3, L4]

Subsequent route points must complete geometry and elevation/ascent/descent updates within **1 second** for representative short Tasmania segments; **500 ms** is the desired target. Preserve the already-fast start-point interaction and accurate route/elevation results. [L1, L6, L7]

Refinement confirmed two additional acceptance requirements: an already-provisioned app with existing ObjectBox data reaches a usable dashboard within **5 seconds** of launch, and ordinary start-point feedback appears within **100 ms** of the accepted click. A usable dashboard is painted, accepts main navigation input, and has loaded its existing local dashboard data and saved settings; an interactive dashboard still loading that data does not satisfy the ceiling. Initial synchronization and first-time dataset imports are measured separately. These targets and the local-data-ready endpoint were confirmed during refinement, not during the original interview.

## User Stories

1. As a MacBook user, I can launch the provisioned app quickly using local Mapping data, even when the mini is unavailable. [L2, L3, L4]
2. As a route planner, I can place subsequent route points and see their route segment and elevation statistics complete within 1 second, ideally 500 ms, without the macOS spinning wheel. [L1, L6, L7]
3. As a Mapping maintainer, I can keep the mini authoritative while app-required dataset changes automatically reach the MacBook as complete, validated replicas. [L3, L4]
4. As a user during a failed or interrupted refresh, I can continue with the previous validated replica and retain a consistent dataset throughout my current app session. [L4, L5]
5. As a user without an initial valid replica, I receive an explanatory unavailable screen and can retry after synchronization completes or quit. [L5]
6. As a developer maintaining both Macs, I can inspect exactly which files are required at startup, during interactive use, and for imports/updates, and compare measured performance before and after localizing them. [L2]

### Dependency inventory and diagnosis

1. Derive the required file set from the current `region_manifest.json` and `Polygons/manifest.json`, using the production schema and path rules. Include the manifests themselves, all referenced regional peaks/highways/polygons, basemap coverage polygons, Natural Features and TasMap catalogs, every declared DEM, and display-polygon references. Do not use a historical count or directory glob as the source of authority. [L2, L3]
2. Produce a maintainer-readable, reproducible inventory containing each store-relative path, current byte size, accessing code, startup existence/readability requirements, startup content reads, live-runtime reads, and import/update reads. Distinguish Mapping source files from the app's local ObjectBox records and caches. State which local copies address frequent or latency-sensitive reads. [L2]
3. The documented baseline is **25 files, 4,255,657,108 bytes (3.963 GiB)**, last audited in the migration documentation on 2026-10-10. The manifests read during this interview on 2026-10-11 retain the documented path set; file sizes and content integrity were not remeasured. Recheck both before provisioning. [L3]
4. Measure startup phases and click-to-complete-update work before and after cutover. Separate manifest/path validation, polygon/catalog work, ObjectBox preparation/imports, route-graph loading/planning, DEM opening, geometry-point sampling, densified summary sampling, and final UI updates where applicable. Record the selected root, filesystem/transport, build mode, dataset identity, route coordinates, and cold-versus-repeated operation conditions. Do not present the suspected SMB cause as proven until measured. [L1, L2, L7]
5. Ordinary first-point placement, except Route-to-peak's immediate routing flow, does not perform segment elevation sampling. Preserve the corrected fast start-point observation and investigate any separately reproduced start-point regression independently. [L1]

### Canonical ownership and local runtime access

1. The mini's `/Volumes/Services/Mapping` remains the authoritative source. The MacBook replica is a downstream copy of the complete manifest-required app dataset; it must not become a competing source for maintainer edits. The Flutter app remains read-only with respect to Mapping datasets. [L3]
2. Support explicit per-machine app runtime-root selection before preflight and ready dependency initialization, using a separate machine-local configuration file under the app's Application Support directory. Support replica mode pointing to a local replica base directory and canonical mode pointing to the mini's directly attached `/Volumes/Services/Mapping`. An absent configuration defaults to replica mode under local Application Support; invalid configuration produces a local configuration diagnostic with `Retry / Quit`, never a canonical/SMB fallback. Keep this file separate from `dart_defines.local.json`, which existing provisioning can copy between machines. Configuration and replica directories remain outside source synchronization roots; exact names may follow project conventions. [L3, L4, L5; refinement]
3. The provisioned MacBook app must not probe the canonical SMB store for readiness/freshness or wait for synchronization before displaying the ready UI. All Mapping-dependent startup, live sampling, and app import/update reads use the selected local generation. Never silently fall back to SMB when the replica is absent or invalid. [L3, L4, L5]
4. Preserve the existing source schema, region/coverage resolution, fingerprints, path containment, preflight requirements, and startup ordering. All declared DEMs remain part of the required dataset even when only ELVIS runtime DEM is sampled interactively. Do not shrink the set by removing manifest declarations or bypassing checks because ObjectBox already exists. [L2, L3]
5. Do not copy the whole Services/Mapping tree. Replicate the manifest-derived app set, keeping raw ELVIS inputs, ELVIS topo DEM, tool-only datasets, Overpass/container state, and unrelated Services content outside the runtime replication set. [L3]
6. Resolve replica selection to a concrete immutable generation directory and propagate that directory through `MappingCatalog.rootPath` and existing read boundaries. A mutable selection pointer may identify a generation, but must not be the root repeatedly resolved by runtime readers. Replica mode uses local storage; canonical mode must not authorize MacBook SMB runtime access. Keep configuration, selection/eligibility records, session protection, and logs separate from immutable dataset payloads. The app may update its local selection/session metadata, but not Mapping dataset contents. [L3, L4; refinement]

### Automatic synchronization and activation

1. Provide a dedicated persistent Mutagen session named **`mapping-runtime-replica`**, with the mini's prepared export directory as **alpha** and MacBook incoming staging as **beta**, using effective mode **`one-way-replica`**. The synchronized source is a prepared manifest-derived export, not the entire canonical Mapping tree. Keep dataset replication separate from the existing three source-workspace sessions and their handover gate. `one-way-replica` may overwrite/remove destination-only content; configuration, local validation records, and retained generations must therefore live outside its destination. [L3, L4; refinement]
2. Install an idempotently managed MacBook user LaunchAgent through maintainer setup tooling. Run the controller at login and every **60 seconds** while the user is logged in. It invokes source preparation over the existing **`mini`** SSH alias, monitors transfer completion, validates local captures, and publishes eligible generations. Reuse unchanged completed exports/generations; a scheduled tick alone must not create another dataset generation. Resume transfers after reconnection and retry failed controller stages on subsequent scheduled runs without involving app startup. Setup must detect existing intended sessions and runner installation, verify effective roots/direction/scope/mode, and reuse matching installations without duplicates; drift is an actionable failure. Expose source-preparation, transfer, validation, eligibility, activation, and cleanup status/errors through maintainer tooling and logs. [L4; refinement]
3. Synchronization writes only incoming staging, never a captured candidate or active replica. A coherent completed source export, completed transfer, and successful validation of an independent local capture are required for eligibility. Detect missing/truncated files, content-digest mismatches, invalid manifest/path references, and inconsistent/interrupted captures. Mutagen reporting idle alone is not evidence of a valid dataset. [L3, L4; refinement]
4. Source preparation and canonical publishers use the coordinated capture and validation contract below. Perform multi-gigabyte hashing and other expensive integrity checks in the background pipeline. Local eligibility must be bound to the validated generation and its integrity inventory, and checkable without repeating those hashes at app launch. Retain normal local preflight and source-read validation. [L2, L4; refinement]
5. Capture received data into a distinct generation directory outside Mutagen's writable destination. Use independent copies or copy-on-write clones, not writable hard links to incoming files. Validate the captured bytes against that source generation's inventory; publish eligibility only after successful validation. An interrupted or inconsistent capture remains ineligible. Never modify an eligible generation: later updates create other generations. Incoming writes during or after validation must not alter captured bytes or make stale validation metadata eligible. [L4; refinement]
6. Activate an eligible completed generation at the next app launch using the transactional selection rules below. Pin the concrete generation for the whole app session, including later imports and lazy DEM opens. Retain it while any session or native dataset handle uses it; do not mutate, delete, or replace its open DEM mid-session. A pending generation never changes the running session's root. [L4; refinement]
7. Interrupted transfer, mini disconnection, source-read failure, corrupt candidate, or local publication failure leaves the previous validated generation usable. Reject/report the failed candidate or capture; do not partially merge it into the active generation. With a valid older replica, the app remains usable while automatic refresh retries later. [L4, L5]
8. Initial provisioning uses the same preparation, transfer, integrity, and activation rules as subsequent refreshes. Document prerequisites, configuration on both machines, coordinated maintenance, runner/session installation and inspection, pause/resume, recovery, and initial synchronization. Pausing runtime refresh is separate from the source-workspace handover gate. [L3, L4, L5; refinement]
9. Install complete, versioned controller and source-preparation artifacts, including their executable dependencies, outside source-workspace synchronization roots on their respective machines. Scheduled invocations must not execute code or resolve executable dependencies from changing working-file checkouts. Install/upgrade through an atomic release selection; pin the selected release and its helpers for the entire invocation, retaining it until that invocation finishes. Source edits, transfers, paused source sessions, and machine handover must not interrupt an installed refresh pipeline or require its source-workspace readiness gate. Expose installed release identities through setup/inspection and logs. Version the pipeline metadata contracts, including source-completion/integrity, durable-receipt, and local eligibility/selection records, and verify supported combinations of the controller, source preparer, and app readers. Upgrades must preserve readability of retained active/recovery generations; incompatible new artifacts fail closed with actionable diagnostics and cannot mutate or delete those generations. Document compatible installation/upgrade and recovery procedures. [L4; refinement]
10. Enforce one mutation-owning controller invocation per replica pipeline across scheduled execution and maintainer commands, including initial provisioning. Later ticks or conflicting commands defer and report busy while healthy work owns the pipeline. The **60-second** schedule is a trigger interval, not a refresh-completion deadline; healthy multi-gigabyte preparation, transfer, capture, and validation may span multiple ticks. Define bounded, noninteractive waits for SSH/process calls, publication/controller lock acquisition, and transfer-status polling; document their limits and distinguish work still progressing from a hung or unavailable stage. On timeout, interruption, or an unknown outcome, record the stage and recoverable operation identity, preserve Mutagen transfer progress and protected data, and never interpret timeout as completion, integrity, or eligibility evidence. Before retrying conflicting work, reconcile any still-running remote preparer or local child through bounded inspection and the operation's ownership/completion evidence. Local controller exit or SSH-client termination alone does not prove remote work ended. Retain each surviving operation's installed release, helpers, and capture/export protection until its ownership actually ends; an unresolved outcome blocks conflicting mutation with actionable recovery diagnostics while later runs may inspect/reconcile it. Document recovery without starting duplicate preparation or releasing another operation's protection. [L4; refinement]

### Coordinated source capture and validation

1. Introduce a mini-local publication lock stored outside the canonical Mapping dataset. Every maintainer operation publishing app-required Mapping files must honor it through publication of related files and manifest/fingerprint changes. A related multi-command update requires one coordinated maintenance transaction, not unlocked gaps between commands. Manual updates follow the same guarded maintenance procedure. Include the necessary existing publisher/tooling and operating-documentation changes in scope; do not enable automatic export until the inventoried publishers comply. [L3, L4; refinement]
2. Snapshot preparation takes the same lock while capturing the complete manifest-derived app set, excluding concurrent publication and partial multi-file update states. An interrupted publication must not be treated as complete merely because its process released the lock: establish completion/recovery evidence before capture resumes. Failed or incomplete source preparation is reported and not published. [L4; refinement]
3. Each export has a generation identity and an integrity inventory containing the manifest pair and every required file's store-relative path, byte size, and **SHA-256** digest. Publish a completion record and make the prepared export visible to synchronization only after capture and source validation succeed. Keep exports and coordination metadata outside the canonical Mapping dataset and source-workspace synchronization roots. [L3, L4; refinement]
4. Distinguish **transfer integrity** (received bytes match the completed source export) from **dataset validity**. Source and local-candidate validation must enforce the production manifest/path rules, required polygon parsing, and declared regional peak fingerprints. Explicitly define additional payload-format checks and their guarantees for peaks, highways, Natural Features, TasMap, display polygons, and DEMs before implementing eligibility. A digest alone is not proof that malformed upstream data is semantically valid. Do not claim validations beyond the documented matrix. [L2, L3, L4; refinement]

### Generation retention and cleanup

1. The background controller owns cleanup. Protect the active generation, one previous validated recovery generation, and every generation pinned by a live app session or native handle. Retain at most one additional eligible pending generation: the newest complete one. Concurrent app launches must not allow selection or cleanup to remove another session's generation. [L4, L5; refinement]
2. Use process-lifetime protection that releases after a crash, rather than permanent flag files that indefinitely imply a live session. Remove superseded unpinned candidates and incomplete captures only after their producing/validating operations have released them. Specify native ownership/release when changing dataset caching or workers. [L4; refinement]
3. Audit space for incoming data, independent capture, protected generations, and mini exports before provisioning/refresh. On insufficient space, report the failed stage and preserve active, recovery, and live-session generations. Do not delete protected data to force publication. [L3, L4, L5; refinement]
4. Do not delete prepared mini exports until the MacBook acknowledges durable independent receipt. Bound unacknowledged export production: complete the existing transfer/receipt or report a blocked pipeline before publishing further exports without bound. Source cleanup must not invalidate an ongoing transfer. [L4; refinement]

### Startup and recovery behavior

1. In replica mode, when no permitted generation passes local readiness, withhold normal ready initialization and show the exact heading **`Mapping runtime replica unavailable`**, affected local paths, and **`Retry` / `Quit`**. Explain that initial synchronization must complete when no initial replica exists; distinguish configuration or validation failures rather than falsely describing every failure as unfinished initial synchronization. Display the selected local root, or the configuration path when selection fails, rather than the hard-coded `/Volumes/Services/Mapping` label. Canonical-mode store failures on the mini retain the existing store-unavailable behavior. [L5; refinement]
2. `Retry` rereads local configuration and rechecks candidate/active readiness using the same transactional launch sequence below. If a complete validated candidate is now available, activate it at this startup boundary and continue normal initialization. If readiness still fails, remain on the explanatory screen with current diagnostics and affected paths. `Quit` exits through the existing startup-shell callback. [L4, L5; refinement]
3. A valid active replica permits startup even with an unavailable mini, disconnected Mutagen session, or rejected pending update. The UI must not falsely claim that this replica contains the latest upstream data. [L4, L5]
4. Preserve the macOS-only platform gate and other startup initialization-error behavior. Keep unavailable-state path lists scrollable, controls keyboard-accessible and reachable at enlarged text scale, and retry work visibly in progress without duplicate concurrent startup attempts. [L5]
5. Remember the existing active selection; check a pending candidate's generation-bound eligibility and run normal local preflight/catalog loading before committing a new selection. Only then atomically select and pin its concrete directory. If candidate checks or selection publication fail, reject/report that candidate and attempt the existing active generation. If the active generation also fails local readiness, attempt the retained recovery generation when present. Withhold ready/ObjectBox initialization until one permitted generation passes local readiness. [L4, L5; refinement]
6. Recover an interrupted selection operation to a complete old or new selection, never partially written metadata. Keep enough local recovery state to preserve the previous valid selection. ObjectBox and other ready-initialization failures retain **`Initialization failed`** behavior and do not automatically roll back Mapping generations. [L4, L5; refinement]
7. For an already-provisioned app with existing ObjectBox data, reach a usable dashboard within **5,000 ms** of app launch. The endpoint is the first presented dashboard frame with its existing local tracks, ascents, list/summary content, and saved dashboard layout/settings loaded, and main navigation able to accept input. Legitimately empty local data may show the normal empty state; provisional empty or loading content in place of existing data does not qualify. Remote tiles and unrelated background work may continue unless they block this endpoint. Measure from a monotonic process-launch timestamp for the already-built macOS app, including native and Flutter startup but excluding compilation, Flutter/Xcode tool startup, and debugger attachment. Correlate that timestamp with a named app readiness marker at the qualifying frame; startup-shell handoff or ready-dependency completion alone is insufficient. Record startup checks, initialization, post-ready local-data loading, and any imports separately; initial synchronization and first-time dataset imports have separate measurements. This ceiling and endpoint were confirmed during refinement. [L1, L2; refinement]
8. The readiness observer must distinguish **pending**, **successfully loaded** (including legitimately empty data or absent saved settings), and **failed** outcomes for every local-data/settings dependency required by the dashboard endpoint. Empty datasets, fallback defaults, or flags set before a read completes are not evidence of successful loading. A failed required read cannot emit the acceptance marker; record a measurement diagnostic identifying the failed dependency. Preserve existing UI fallback/error behavior. All required dashboard data/settings, including those serving off-screen cards, must have loaded successfully; visible cards must present current content in the qualifying frame. Off-screen widgets may remain lazily constructed and do not need to be built or scrolled into view before the marker. [L1, L2; refinement]
9. Before startup optimization, fix a reproducible startup workload in the diagnosis benchmark record: relevant ObjectBox record counts and stored track-geometry vertex counts, migration/backfill status, saved dashboard order and relevant settings, window size, text scale, and cold/repeated launch conditions and repetition counts, alongside the existing dataset identity and build-mode evidence. Hold the local-data and presentation workload constant between comparable before/after runs; record deviations as different workloads rather than interchangeable acceptance evidence. Use non-sensitive read-only summaries; do not copy personal databases, GPX content, or private configuration into workflow artifacts. [L1, L2; refinement]

### Route-point behavior and performance

1. For the recorded representative short Tasmania segment cases, elapsed time from the accepted point-placement click to the visible committed/snapped segment **and refreshed elevation, ascent, and descent** must be at most **1,000 ms**. Aim for **500 ms**. Measure both the first subsequent point after launch, including any lazy DEM open, and repeated subsequent placements. Marker appearance or readiness for another click alone does not satisfy this target. [L6, L7]
2. Ordinary start-point feedback must be visible within **100 ms** of the accepted click, a ceiling confirmed during refinement. Preserve immediate click feedback and distinguish Route-to-peak's immediate routing flow from ordinary first-point placement. Route/elevation work must not produce the macOS spinning wheel or block map interaction, including during longer calculations outside the short-segment benchmark. [L1, L7; refinement]
3. Preserve route geometry, endpoint snapping, elevation sampling accuracy, summary semantics, point ordering, undo/redo, saving, and existing mode-specific behavior. Investigate remaining measured CPU/I/O or rendering bottlenecks if local storage alone does not meet the complete-update target. [L2, L6, L7]
4. Preserve the existing routing-in-progress guards for accepting additional point-placement actions, and preserve cancellation/request-version checks so obsolete routing/elevation results cannot update a canceled or newer draft. Loading must remain renderable while async work is pending. [L7]
5. Preserve visible route/elevation error and retry behavior for failures reading the selected local source. Logs must include operation and local dataset context; errors must not trigger hidden SMB access or silently replace failed elevation calculations with success. [L2, L5, L7]
6. The initial diagnosis must fix a reproducible benchmark record before optimization begins: exact real Tasmania point sequences in primary **Snap-to-trail** mode, both fresh and accumulated multi-point drafts, new-segment and cumulative draft lengths, geometry vertex counts, dataset identity, build mode, existing ObjectBox/graph state, and repetition count. Exercise fresh launches including first lazy DEM/graph access and repeated-use cases. Measure through the frame displaying committed geometry and current statistics; report individual placements and their maximum, not an average substituted for the ceiling. Exercise Straight-line and Route-to-peak for correctness/responsiveness and report their timings separately. The original affected mode remains unknown. [L1, L2, L6, L7; refinement]
7. Preserve elevation results and summary semantics, not mandatory whole-draft raster rereads. Profiling may justify reusing unchanged DEM samples and sampling only new/changed geometry before recomputing summaries from combined samples. Existing three-point ascent/descent smoothing changes values around an appended segment boundary, so independently summing segment totals is not an equivalent replacement. Account for snapping, edits, undo/redo, dataset-generation changes, and request/geometry-version invalidation. Reuse is permitted, not an unmeasured claim that caching alone meets the targets. [L2, L6, L7; refinement]

## Technical Decisions

- Keep the Flutter/Riverpod/ObjectBox architecture and production manifest parsers. `MappingDataStoreCore` already accepts an injected `rootPath`, and `MappingCatalog.rootPath` drives validated consumers; use that boundary to select the app's local generation. Machine-specific selection must occur before `StartupShell` reaches ready initialization. [L3, L4]
- Keep maintainer tools' canonical-source authority distinct from app runtime-root selection. Any new snapshot publisher must comply with existing Mapping read/capability and publication boundaries. Replica provisioning writes downstream staging/generation metadata, not canonical Mapping datasets. [L3, L4]
- Add only narrowly scoped owners/capabilities for snapshot reads, non-store export/replica publication, coordination, and local selection/session metadata. Update the maintainer inventory and direct-I/O guard coverage for these boundaries; do not bypass existing resolver authority, import tool manifests into shipped runtime, or broadly relax the I/O allowlist. Canonical publisher coordination retains each tool's existing dataset-write authority. [L3, L4; refinement]
- Pin an immutable local generation for each app session. Staging/transfer progress is not app readiness; eligibility derives from completed local validation. A candidate arriving during a running session becomes available for a future launch, not a live source replacement. [L4]
- Use transport/process/filesystem seams for replication and activation tests. Prefer existing injected filesystem, DEM opener/sampler, route planner, startup coordinator, and quit callback seams. Add narrowly scoped seams only for new nondeterministic synchronization/activation boundaries. [L4, L5, L7]
- Moving reads to local storage is the agreed primary solution shape, not proof that synchronous GDAL or route-graph work is harmless. Profile residual work; expensive raster/CPU work must not monopolize Flutter's UI isolate. If workers or cached native datasets are changed, define their ownership and cleanup and preserve geometry/request-version invalidation. [L2, L6, L7]
- Bulk copy, synchronization, integrity validation, and snapshot publication belong to the background maintainer pipeline, not a blocking network operation embedded in app launch or route clicks. Preserve host GDAL/PROJ dependencies and existing DEM selection. [L3, L4]
- Local paths and SSH/session configuration are non-secret configuration. Reuse normal SSH authentication without embedding passwords, private keys, API keys, or tokens in scripts, logs, workflow artifacts, or synchronized dataset metadata.
- This change supersedes the SMB-only MacBook app-runtime restriction and the prohibition on a **dedicated runtime-data** replication session in Spec 0062 and associated docs. Preserve the three source sessions, mini canonical ownership, source/data boundaries, and personal-data locality. Update current operating docs with the new runtime contract while retaining historical migration evidence. [L3, L4]

## Testing Strategy

### Deterministic automated coverage

- **TDD default:** use behavior-first red/green/refactor for new replica selection, eligibility, publication, startup state, and async-result logic. Existing contracts and tests are the baseline; no automated test depends on the user's real Mapping files, SMB share, SSH credentials, or API keys.
- **Service/unit tests:** derive the complete dependency set from fixture manifests; check required DEMs/display polygons, deduplication, invalid/path-escaping references, digest mismatch/truncation, declared peak fingerprint mismatch, and the agreed payload-validation matrix. Exercise publisher/capture exclusion, incomplete multi-command publication and publisher crash recovery, incomplete transfers, independently captured generation eligibility, and eligibility bound to exact generation contents. Mutagen writes during/after validation cannot alter an eligible capture; changed captures remain ineligible. Cover atomic selection and retention of the previous valid generation. [L3, L4; refinement]
- **Synchronization/runner tests:** use disposable directories and fake process/status/clock responses, plus disposable real Mutagen endpoints where meaningful, to verify mini-alpha/MacBook-beta direction, effective `one-way-replica`, reconnect catch-up, scope, setup reuse/drift detection, and incoming-only writes. Check login/60-second scheduling, unchanged-generation reuse, failed-stage retry, controller restart, and that app startup never dispatches/waits for the runner. Exercise source edits/partial source delivery, paused source sessions, and handover during a scheduled refresh: installed artifacts remain executable without consulting the source-workspace gate. Cover atomic runner/source-preparer upgrades, invocation-pinned helper/dependency versions, retained in-use releases, supported metadata-version combinations, and incompatible-artifact rejection without changing active/recovery generations. A live canonical Mapping source must not be edited to manufacture failures. Verify selected files are not omitted merely because their contents are rarely read interactively; destination-only metadata must never be placed inside the replica session. [L3, L4; refinement]
- **Controller execution/recovery tests:** use deterministic process, transport, lock, status, and clock seams to verify healthy work spanning multiple 60-second ticks, overlapping scheduled/maintainer/initial-provisioning invocations, bounded noninteractive waits, and hung or unavailable stages. Verify later conflicting invocations defer rather than duplicate mutation. Exercise controller interruption and SSH-client termination while a remote preparer or local child remains alive: subsequent runs reconcile the recorded operation identity before conflicting retries, and unresolved outcomes report blocked recovery. Surviving work retains its release/helpers and capture/export protection until ownership ends. Timeouts never publish completion/eligibility, erase Mutagen transfer progress, or remove protected generations; confirmed failure/completion permits the appropriate safe retry or continuation. Use disposable data and controlled processes, not the live canonical store. [L4; refinement]
- **Startup widget/coordinator coverage:** absent configuration selects the local replica default; invalid configuration reports its local path and remains retryable; explicit mini canonical selection retains existing behavior. Missing initial replica shows the exact heading, local paths, and `Retry / Quit`; a completed initial transfer becomes ready on retry; a failed retry remains recoverable; Quit invokes its callback; existing valid replica starts with remote access configured to fail. Candidate preflight failure and selection-publication failure fall back to the valid active generation; a failed active generation permits the retained valid recovery generation; interruption around activation recovers a complete selection. Verify no ready/ObjectBox initialization before local readiness, no duplicate retry dispatch, and no dataset rollback for ready-initialization errors. Cover scrollable errors at enlarged text scale and keyboard-reachable actions using established widget patterns. [L4, L5; refinement]
- **Retention coverage:** verify active/recovery protection, newest-pending pruning, live-session/native-handle protection during cleanup, overlapping launches, crash-released session protection, removal of abandoned unowned captures, and low-space publication failure without deleting protected generations. Mini export cleanup requires durable-receipt acknowledgement and cannot disrupt an ongoing transfer; failed acknowledgement/reconnection must not produce unbounded exports. [L4, L5; refinement]
- **Provider/elevation coverage:** assert selected local-generation paths reach the DEM opener, source errors remain visible/retryable, output geometry/elevation summaries retain their semantics, and cancellation/new geometry rejects stale results. Reuse `FakeDemFileSystem`, `FakeDemDatasetOpener`, `LookupDemDataset`, and existing route planner/sampler injection. Pending fake work must permit pumping frames and interacting with supported controls. [L1, L6, L7]
- **Sample-reuse regression coverage, if introduced:** compare combined cached/new sampling results with the existing full-recomputation baseline, including append-boundary smoothing, endpoint snapping, edits, undo/redo, and generation changes. A selection change must not redirect a running session's late imports or lazy DEM opens to a new generation. [L4, L6, L7; refinement]
