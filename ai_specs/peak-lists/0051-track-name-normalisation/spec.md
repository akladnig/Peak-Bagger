type: Spec
title: Track Name Normalisation
---

## Problem

Imported `GpxTrack.trackName` values can include the walk date from GPX metadata or the filename, even though the date is already stored separately as `GpxTrack.trackDate`. This produces redundant and inconsistent Track labels across maps, search, peak ascent history, and exports. Existing Tracks need a safe bulk repair, and new imports must not reintroduce the date suffix. [L1]

## Proposed Outcome

Provide a Track name normalisation operation in Settings that removes only supported trailing date suffixes from persisted Track names while preserving each Track's separate date and all other data. Apply the same canonicalisation to all future GPX import names, including user-edited import names. [L1] [L2]

## User Stories

1. As a user maintaining recorded walks, I can normalise stored Track names from Settings so labels show the walk name rather than a redundant trailing date. [L1] [L3]
2. As a user importing a new GPX Track, I receive the same date-free Track name without needing to run the maintenance action again. [L1] [L2]
3. As a user, I can cancel the bulk action safely and receive a clear completion or failure result when I run it. [L3]

## Requirements

1. Add a Settings `ListTile` directly below `Recalculate Track Statistics` with key `normalise-track-names-tile`, title `Normalise Track Names`, and subtitle `Remove trailing dates from stored track names`. [L1] [L3]
2. Tapping the tile must show a confirmation dialog with title `Normalise Track Names?`, message `This will remove trailing dates from stored track names. Track dates will be kept. Do you wish to proceed?`, `Cancel`, and `Normalise` actions. Use keys `normalise-track-names-cancel` and `normalise-track-names-confirm`. Cancelling must make no persistence changes. [L3]
3. The action must inspect every persisted `GpxTrack` and replace only a supported trailing date suffix in `trackName`; its `trackDate`, identifier, GPX XML, derived statistics, peak relations, visibility, and other persisted fields must remain unchanged. [L1] [L2]
4. A supported suffix is a terminal real calendar date formatted exactly `dd-MM-yyyy` or `dd/MM/yyyy`, optionally wrapped in parentheses. The separator between a non-empty name and suffix may be absent or may contain any whitespace, hyphen, or underscore characters; trailing whitespace after the suffix is allowed. Remove that separator with the suffix and trim the resulting name. The suffix date does not need to equal `trackDate`. [L2]
5. Do not modify a date that is not at the end of the Track name. Do not replace a name made solely of a supported date suffix with an empty name. Do not alter invalid calendar dates, other date shapes such as a standalone year, or embedded dates. Examples: `MtAnne10-03-2025` becomes `MtAnne`; `Mt Anne (10-03-2025)   ` becomes `Mt Anne`; `Mt Anne 31-02-2025` remains unchanged. [L2]
6. The success dialog must be titled `Track Names Normalised`, use close key `normalise-track-names-result-close`, and report `Updated N tracks, unchanged N tracks`, using the app's count formatting. [L3]
7. If the operation fails, set `trackImportError` to exactly `Failed to normalise track names: $e`, then show `Track Name Normalisation Failed` with close key `normalise-track-names-error-close` and that error detail. Stored Track names must remain as they were before the operation began. [L3]
8. While Track name normalisation, Track-data reset, or Track-statistics recalculation is in progress, disable only `Reset Track Data`, `Recalculate Track Statistics`, and `Normalise Track Names` consistently with `MapState.isLoadingTracks`; keep `Track Speed Analysis` available. Show the standard compact progress indicator in the active tile. [L3]
9. Update the in-memory map Track list after a successful operation so all visible Track labels and dependent peak-info content use the persisted normalised name without requiring app restart or navigation refresh. [L1] [L3]
10. Apply the same normalisation to every incoming GPX Track name, whether derived from GPX content, a filename fallback, or a user edit in the selective import dialog, before duplicate/replacement matching and persistence. Compare both incoming and existing stored names through the same normaliser for duplicate/replacement matching, without bulk-updating unmatched existing Tracks. A logical match requires both Tracks to satisfy the existing `GpxTrack.hasMetadataTrackDate` predicate and to share the same normalised name and Track date. For exactly one logical match in selective import, retain the stored `gpxTrackId`, replace its imported Track content with the incoming Track, recompute its peak correlation using the existing import behavior, and select the replaced Track when the import completes. Resolve its managed destination using the existing replacement-destination rule. When a managed file already exists at that destination, back it up, move the incoming file into its place, persist the Track replacement, then remove the backup. If any managed-file or database stage fails, restore the managed file and incoming source file to their pre-operation locations, leave the stored Track unchanged, and count that incoming Track as an error. If restoration cannot complete, the recovery-issue contract in technical decision 10 applies instead. Count a completed replacement as replaced. Process selected incoming files in selected-file order. If a later eligible incoming Track is a logical match for an earlier eligible incoming Track in the same selection, make no persistence or managed-file changes for the later Track, count it as an error, append exactly `Cannot import Track because another selected Track has the same normalised name and date.` to `import.log`, and retain that exact per-file error. The selective-import plan and result must retain added, replaced, unchanged, unsupported, and error counts, plus ordered per-file errors with `sourcePath` and exact `reason` fields. If multiple stored Tracks are logical matches, make no persistence or managed-file changes for that incoming Track, count it as an error, append exactly `Cannot replace Track because multiple stored Tracks match its name and date.` to `import.log`, and retain that exact per-file error. [L1] [L2]
11. The selective-import summary must report exactly `Added N tracks, replaced N tracks, unchanged N tracks, unsupported N tracks, errors N tracks`, using the app's count formatting for every `N`. [L1] [L2]

## Technical Decisions

1. Define one reusable Track-name normalisation boundary and call it from GPX import parsing, user-edited import-name handling, duplicate/replacement comparison, and the bulk maintenance operation. Do not duplicate date-matching regular expressions across UI, importer, or persistence code. [L1] [L2]
2. Keep `GpxTrack.trackName` as the canonical persisted display name and `GpxTrack.trackDate` as the canonical calendar day. The operation must not parse, overwrite, or delete `trackDate`. [L1]
3. Expose the bulk operation through the existing `MapNotifier`/`mapProvider` Track-operation boundary, returning a result with updated and unchanged counts. Set and clear `MapState.isLoadingTracks` and surface errors through the established track-operation error state. [L3]
4. Expose a repository-level batch name-normalisation operation. Back it with one ObjectBox write transaction and provide an in-memory transactional implementation or injectable batch-write failure seam for deterministic rollback tests. A write failure must roll back all name changes; refresh state and report counts only after commit succeeds. [L3]
5. Refresh provider state from persisted Tracks after success. The operation changes labels only: it must not recalculate statistics or peak correlation, but it must refresh label consumers such as peak-info popup content. [L1] [L3]
6. In `lib/services/peak_info_content_resolver.dart`, use the shared normaliser first and then retain the current display-only legacy fallback regex `r'\s*\(\d{1,2}/\d{1,2}/\d{4}\)$'`. The fallback is non-validating, supports one- or two-digit day and month components, must not modify persisted data, and must not replace the shared normaliser. [L1]
7. Extend the selective-import plan/result and completed background-job summary/details to carry `replacedCount` and ordered per-file errors with `sourcePath` and exact `reason` fields. The summary must use requirement 11's exact five-count text. After its count lines, details must include every retained error in selected-file order as exactly `<basename(sourcePath)>: <reason>`. [L1] [L2]
8. For a logical replacement, retain the existing `gpxTrackId`, `visible`, and `trackColour`. Replace GPX-derived and derived Track content from the incoming Track, then recompute peak correlation. The database persistence stage is one ObjectBox write transaction that replaces the Track, its `peaks` relation, and the affected `PeaksBagged` rows; a failure commits none of those changes. [L2]
9. The selective-import plan's added, replaced, unchanged, unsupported, and error counts are prospective outcomes after parsing and matching. The completed result's five counts are actual completed outcomes and include execution-stage errors. Both retain planning-stage errors; the completed result additionally retains execution-stage errors, all in selected-file order. Every error record has exactly `sourcePath` and `reason`. The existing exact same-selection and multiple-stored-match reasons remain unchanged. Use these exact reasons for execution failures: `Cannot replace Track because its managed-file destination could not be resolved.`, `Cannot replace Track because the existing managed file could not be backed up.`, `Cannot replace Track because the incoming managed file could not be moved.`, `Cannot replace Track because the Track replacement could not be persisted.`, `Cannot replace Track because the managed-file rollback could not be completed.`, `Cannot replace Track because the managed-file backup could not be removed.`, and `Cannot replace Track because restoration could not be completed. Recovery is required.` [L2]
10. For requirement 10's managed-file/database replacement sequence, a backup-cleanup failure is a replacement failure. Attempt to restore the managed file, incoming source file, stored Track, its `peaks` relation, and affected `PeaksBagged` rows to their pre-operation state. If restoration cannot complete, persist a `TrackReplacementRecoveryIssue` containing exactly the affected `sourcePath`, `destinationPath`, nullable `backupPath`, and failure `reason`; leave the stored Track unchanged; and report the replacement as an error rather than a success. A pending issue blocks all Track operations. Provide a Settings recovery action that reconciles the recorded paths to their pre-operation state and clears the issue only after successful reconciliation. [L2]
11. Selective-import managed-file operations must use one injectable boundary that supports deterministic failures for destination resolution, backup, incoming move, source restoration, managed-file restoration, and backup cleanup. [L2]

## Out of Scope

- A persistent user preference that selectively enables or disables Track name normalisation. [L1]
- Removing, changing, or deriving `trackDate` from Track names. [L1]
- Normalising arbitrary embedded dates, standalone years, or date formats outside the agreed terminal `dd-MM-yyyy` and `dd/MM/yyyy` forms. [L2]
- Changing an already persisted manually edited Track name except when the explicit bulk action is run. A name entered during a new import is normalised under requirement 10.
- Recalculating Track statistics or peak correlation as part of the bulk Track name normalisation action. [L3]
